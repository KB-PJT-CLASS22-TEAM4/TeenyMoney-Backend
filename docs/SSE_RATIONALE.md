# SSE를 선택한 이유

실시간 화면 동기화 채널로 SSE(Server-Sent Events)를 골랐다. 이 문서는 그 선택을 방어한다.

**먼저 밝힌다: 측정하지 않았다.** 이 프로젝트에는 부하 테스트가 없다. 그래서 "SSE가 더 빠르다",
"폴링보다 서버 부담이 적다" 같은 말은 이 문서에 쓰지 않는다. 측정 없이 성립하는 근거만 쓴다.

실제 근거는 하나다. **알림과 데이터 동기화가 지금 한 채널에 묶여 있고, 그걸 떼어놔야 한다.**

---

## 1. 왜 FCM으로 부족한가

FCM은 이미 20곳에서 쓴다. 그런데 `NotificationService.createNotification()`은 회원의 알림 설정이
꺼져 있으면 푸시를 보내지 않고 return한다.

```java
// 퀘스트 관련 알림을 끈 경우
if (notificationReferenceType == NotificationReferenceType.QUEST
        && !memberNotificationVO.getNotiQuest()) {
    return;
}
```

여기서 죽는 것이 푸시 하나면 정상이다. 문제는 **화면 갱신도 같이 죽는다**는 것이다.

자녀가 퀘스트 푸시를 껐다고 하자. 그래도 자녀가 앱에서 퀘스트 목록을 보고 있다면 부모가 방금
만든 퀘스트는 화면에 떠야 한다. 알림 끄기는 "그만 찔러라"이지 **"화면을 낡은 상태로 두라"가
아니다.** 부모 쪽은 더 심각하다. 부모가 알림을 껐다고 자녀의 승인 요청이 요청함에 안 뜨면,
자녀는 아무 이유 없이 계속 기다린다.

부차적 근거 둘:

- **FCM 토큰이 없는 사용자가 있다.** `firebase.js`의 `requestFcmToken()`은 브라우저가 지원하지
  않거나 권한이 거부되면 `null`을 반환하고 끝난다. 그 사용자들은 지금 실시간성이 전혀 없다.
- **잔액 같은 상태 값을 FCM data 페이로드로 밀어넣는 것은 알림 채널의 오용이다.** 알림은
  사용자를 부르는 수단이지 데이터 전송로가 아니다.

정리하면, FCM은 **앱 밖에서 사용자를 부르는** 일을 하고, SSE는 **앱 안에서 화면을 최신으로
유지하는** 일을 한다. 지금은 하나가 둘 다 하고 있어서, 하나를 끄면 둘 다 꺼진다.

---

## 2. 왜 폴링이 아닌가

`LinkCode.vue`에 3초 폴링 골격이 주석으로 남아 있었다. 내용은 이랬다.

```js
//   pollingInterval = setInterval(async () => {
//     // TODO: 연동 완료 확인 API 연동
```

**구현된 적이 없다.** 확인 API도 없다. 살렸다면 코드 유효기간 10분 동안 200번 요청하고
그중 199번은 빈 손으로 돌아왔을 것이다. 그리고 그건 연동 화면 하나 얘기다. 자녀 홈, 퀘스트
목록, 부모 요청함까지 같은 방식으로 채우면 화면 수만큼 빈 요청이 곱해진다.

이 근거는 성능 측정이 아니라 산수다. "변경이 없어도 주기적으로 묻는다"와 "변경이 있을 때만
한 번 묻는다"의 차이다.

---

## 3. 왜 WebSocket이 아닌가

**완전 단방향이기 때문이다.** 클라이언트가 이 채널로 서버에 보낼 것이 하나도 없다. 사용자의
모든 행동은 이미 기존 REST API를 탄다.

WebSocket을 쓰면 핸드셰이크, 프로토콜 업그레이드, 프레임 처리, 하트비트 프레임을 전부 들여오는데
그중 절반은 우리가 쓰지 않는 방향(클라이언트 → 서버)을 위한 것이다. SSE는 그냥 HTTP 응답을
닫지 않고 두는 것이라 기존 서블릿 스택 위에서 그대로 돈다.

실제로 `WebConfig`를 한 줄도 고치지 않았다. `AbstractAnnotationConfigDispatcherServletInitializer`가
서블릿과 필터 모두에 `asyncSupported=true`와 `DispatcherType.ASYNC` 매핑을 이미 걸어주기 때문이다.

---

## 4. 왜 이벤트에 데이터를 싣지 않는가

서버는 이벤트 이름만 보낸다.

```
event: QUEST
data: {}
```

클라이언트는 이 신호를 받으면 **기존 조회 API를 다시 호출한다.**

- **새 DTO가 0개다.** SSE 전용 응답 스키마를 만들지 않았다.
- **정합성이 한 곳에서만 결정된다.** 이벤트 페이로드와 조회 API 응답이 서로 어긋나는 버그가
  원천적으로 생길 수 없다.
- **인가 검사가 기존 API 것을 그대로 탄다.** SSE 경로에 "이 사람이 이 퀘스트를 볼 수 있나"를
  다시 구현하지 않는다. 복제된 권한 로직은 반드시 원본과 어긋난다.
- **유실 복구가 공짜다.** 연결이 끊긴 동안 놓친 이벤트가 있어도, 재연결 후 화면이 한 번
  조회하면 최신 상태가 된다. 그래서 `Last-Event-ID` 재전송 장치를 만들지 않았다.

"그럼 결국 폴링 아닌가"에 대한 답: 요청이 **변경이 있을 때만 한 번** 나간다. 주기적으로 빈
응답을 받지 않는다.

---

## 5. 왜 발행이 20곳이 아니라 한 곳인가

이 설계에서 가장 많이 바뀐 부분이다.

처음에는 "퀘스트 생성 / 용돈 송금 / 가족 연동" 세 곳에 발행 한 줄씩 넣으려 했다. 그런데
`createNotification()` 호출 지점을 전수조사하니 **20곳**이었고, 세 곳은 그중 일부였다.
더 중요하게는 **자녀 → 부모 방향이 통째로 빠져 있었다.**

| 자녀 행동 | 부모 화면에서 낡는 것 | 지점 |
|---|---|---|
| 오늘만 허용 요청 | 요청함 | `PermissionService:159` |
| 퀘스트 인증 제출 | 요청함 | `QuestProgressService:132` |
| 금융상품 가입 신청 | 요청함 | `FinancialProductEnrollmentService:158` |

이 앱은 **승인 워크플로**다. 자녀가 요청하고 부모가 승인한다. 그리고 기다리는 쪽은 주로
자녀다. `useParentRequests.js`가 이 세 가지를 한 목록으로 합쳐 `Parents/RequestList.vue`에
띄우는데, 그 화면이야말로 늦으면 안 되는 화면이었다.

20곳에 한 줄씩 넣으면 21번째가 생길 때 조용히 빠진다. 그래서 **20곳이 전부 지나는 한 곳**에
넣었다.

```java
notificationMapper.insert(notificationVO);

// ── 화면 동기화 ──
eventPublisher.publishEvent(new SseEvent(memberId, notificationReferenceType));

// ── 여기부터 알림 ──
if (isPushed == null || !isPushed) return;
if (referenceType == QUEST && !vo.getNotiQuest()) return;
```

**발행이 설정 검사보다 위에 있다는 것이 이 설계의 전부다.** 아래로 내리면 1절에서 말한 문제가
그대로 돌아온다. "알림과 동기화의 분리"가 문서가 아니라 코드 세 줄 간격으로 드러난다.
`NotificationServiceTest`에 그 순서를 지키는 회귀 테스트를 두 개 뒀다.

이벤트 이름은 `NotificationReferenceType` 값을 그대로 쓴다. 새 카탈로그를 만들지 않은 이유는
**그게 이미 카탈로그이기 때문이다.** 매핑 코드가 0줄이다.

치르는 값도 적어둔다. SSE가 `NotificationService`에 얹혀서, 알림 이력을 남기지 않는 상태
변경은 이 방식으로 잡히지 않는다. 실제로 두 군데 있고, 다음 절이 그 얘기다.

---

## 6. 왜 알림 수신자와 동기화 수신자가 갈리는가

알림 수신자는 **"누구에게 알릴까"**의 답이고, 동기화 수신자는 **"누구 화면이 낡았나"**의 답이다.
대부분 같지만 두 군데에서 갈린다.

**A. 송금할 때 부모 지갑.** `TransferService`는 받는 자녀에게만 알린다. 보내는 부모에게
"당신이 방금 보냈습니다" 알림을 보내는 건 성가신 짓이니 맞는 결정이다. 하지만 부모 지갑도
함께 줄어든다. 특히 정기 용돈(`AllowanceScheduleProcessor`)은 **새벽에 자동으로 실행되므로**
부모는 아무 행동도 하지 않았고, 응답으로 화면이 갱신될 기회조차 없다.

**B. 자녀가 결제할 때 부모가 보는 자녀 지갑.** `PaymentService`는 '주의 업종 + 티니등급 3 이하'일
때만 부모에게 알린다. 그것도 맞는 결정이다. 하지만 부모 홈은 결제 종류와 무관하게 자녀 지갑을
보고 있어서 **모든 결제마다** 낡는다.

그래서 이 두 곳만 명시적으로 발행한다. 각각 한 줄이고, 5절의 한계를 드러내는 표본 역할도 한다.

---

## 7. 왜 "커밋 이후"가 아니라 "데이터가 보인 이후"인가

커밋 전에 신호를 쏘면 클라이언트가 곧바로 조회 API를 호출하고, 그 조회는 **아직 커밋되지 않은
데이터를 보지 못한다.** 화면이 갱신 안 된 채로 남고, 재현이 어려운 타이밍 버그가 된다.

그래서 `@TransactionalEventListener(phase = AFTER_COMMIT)`을 쓴다. 롤백되면 리스너가 아예
실행되지 않는 성질도 공짜로 따라온다.

여기에 함정이 있었다. 이 애노테이션은 **활성 트랜잭션이 없으면 예외도 로그도 없이 리스너를
통째로 건너뛴다**(기본 `fallbackExecution = false`). 그리고 이 코드베이스에는 트랜잭션 밖에서
알림을 보내는 자리가 둘 있다.

| 지점 | 왜 트랜잭션이 없나 |
|---|---|
| `TransferService.executeTransfer` | `@Transactional(propagation = NOT_SUPPORTED)` — 락과 실패 기록이 얽혀 데드락이 나던 문제 때문에 **일부러** 뺐다 |
| `QuestProgressService.submitVerification` | S3 업로드를 트랜잭션 밖에 둬야 해서 `transactionTemplate`을 쓴다 |

두 자리 모두 **데이터는 이미 커밋된 뒤**다. `lockAndMove()`가 자기 트랜잭션을 끝냈고, 인증
이력도 저장이 끝났다. 즉 기다릴 것이 없고 즉시 발행하는 것이 맞다.

그래서 규칙을 다시 썼다. **"커밋 이후"가 아니라 "데이터가 보이게 된 이후"다.**

```java
@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)
```

트랜잭션이 있으면 커밋 후, 없으면 즉시. 한 줄이 둘 다 만족시킨다.

(실제로는 5절 덕분에 이 문제가 대부분 사라졌다. `createNotification()` 자체가
`@Transactional`이라 호출자에게 트랜잭션이 없으면 거기서 새로 열린다. `fallbackExecution`은
6절의 명시적 발행 두 줄을 위한 안전판으로 남겼다.)

## 8. 티켓을 쿼리 파라미터에 넣는 것의 위험과 완화

브라우저 네이티브 `EventSource`는 **`Authorization` 헤더를 붙일 수 없다.** 우리 인증은
`Authorization: Bearer`라서 여기서 부딪힌다.

**쿼리 파라미터는 서버 액세스 로그에 남는다.** 이게 이 설계에서 방어해야 할 지점이다.

그래서 액세스 토큰을 넣지 않고, 별도의 1회용 티켓을 발급한다.

```
POST /api/v1/sse/ticket          (Bearer 필요)  → { "ticket": "<uuid>" }
GET  /api/v1/sse/subscribe?ticket=<uuid>        → text/event-stream

sse:ticket:{uuid} → "{memberId}"   TTL 30초
```

- 소비는 `GETDEL`이라 조회와 삭제가 한 명령이다. 같은 티켓으로 둘이 동시에 붙어도 성공하는
  쪽은 하나뿐이다. `FamilyLinkCodeStore.consumeCode`와 같은 방식이라 새 개념이 아니다.
- 로그에 남더라도 **이미 소비됐거나 30초 뒤 사라진 값**이다. 액세스 토큰이었다면 30분짜리
  유효한 자격증명이 로그에 평문으로 쌓였을 것이다.

**쿠키를 쓰지 않은 이유**: 프로덕션은 동일 출처라 `EventSource`가 쿠키를 자동으로 싣는다.
하지만 지금 쿠키에 있는 것은 Refresh Token이고, 그걸 30분짜리 스트림의 인증 수단으로 삼으면
Access Token을 30분으로 줄인 의미가 깎인다. `JwtAuthenticationFilter`도 쿠키를 읽지 않는다.

**치른 값**: 티켓이 1회용이라 `EventSource`의 자동 재연결은 **반드시 실패한다.** 같은 URL로
다시 붙는데 그 티켓은 이미 소비됐기 때문이다. 그래서 클라이언트가 `onerror`에서 직접 닫고
티켓을 새로 받아 다시 연결한다(지수 백오프 1초 → 최대 30초). 이 처리를 빠뜨리면 첫
타임아웃 이후 실시간성이 조용히 사라지므로, 재연결 코드는 선택이 아니라 필수다.

## 9. 왜 하트비트가 애플리케이션 스케줄러를 쓰지 않는가

하트비트(`:ping`)는 두 가지를 한다 — 중간 프록시의 idle timeout으로 연결이 끊기는 것을 막고,
사라진 클라이언트를 전송 실패로 감지해 정리한다(서버는 쓰기 전까지 끊긴 걸 모른다).

`@Scheduled`로 붙이는 게 자연스러워 보이지만 그러면 안 된다. `RootConfig`에 `TaskScheduler`
빈이 없어서 **기본 스레드 풀 크기가 1**이고, 그 한 스레드를 야간 배치들이 공유한다.
`AllowanceScheduler`와 `FinancialProductMaturityScheduler`는 둘 다 `0 10 0 * * *`이다.

- 00:10 배치가 N분 돌면 그동안 `:ping`이 한 번도 안 나가고 → **매일 새벽 전 연결이 죽는다**
- 반대로 하트비트가 죽은 소켓 쓰기에서 블록되면 → 용돈 배치가 밀린다

하트비트는 SSE의 인프라이지 애플리케이션 배치가 아니다. 그래서 `SseEmitterRegistry`가
`Executors.newSingleThreadScheduledExecutor()`를 직접 들고 `@PreDestroy`로 닫는다.
`RootConfig`는 한 줄도 고치지 않았다.

> 배치 5개가 풀 크기 1을 공유하는 것 자체는 SSE와 무관한 기존 문제다. 같은 시각 두 배치가
> 이미 직렬화되고 있다. 별도 이슈로 올린다.

`SseEmitter.send()`는 스레드 안전하지 않아서, 하트비트 스레드와 이벤트 스레드가 같은 에미터에
동시에 쓰면 스트림이 섞이거나 `IllegalStateException`이 난다. 전송은 **에미터 단위로**
동기화한다(전역 락이 아니다).

## 10. 확인하지 못한 것

**프로덕션 리버스 프록시 구성.** `docs/DEPLOY.md`에 기록이 없다. nginx가 앞에 있다면
`proxy_buffering`이 기본 on이고, 그러면 **이벤트도 하트비트도 한 글자도 내려가지 않는다.**
연결은 열려 있는 것처럼 보여서 더 헷갈린다.

인프라 설정을 못 건드리는 상태에서 할 수 있는 완화를 넣었다 — 구독 응답에
`X-Accel-Buffering: no` 헤더. nginx에게 이 응답만은 버퍼링하지 말라고 말하는 표준 수단이다.

**두 시간 값도 측정하지 않았다.** 그래서 상수로 박지 않고 프로퍼티로 뺐다.

```
sse.heartbeat-interval-ms=${SSE_HEARTBEAT_INTERVAL_MS:25000}
sse.emitter-timeout-ms=${SSE_EMITTER_TIMEOUT_MS:1800000}
```

25초는 로컬 Vite 프록시가 idle 60초(`vite.config.js`)이고 nginx 기본값도 60초라 2배 여유를
둔 값이다. 실측 후 재배포 없이 조정할 수 있다.

## 11. 단일 인스턴스 가정과, 다중화될 때 깨지는 것

지금은 단일 EC2, 단일 Tomcat이다. 그래서 열린 연결을 JVM 메모리
(`ConcurrentHashMap<Long, Set<SseEmitter>>`)에 들고 있다. Redis pub/sub을 넣지 않았다.

**인스턴스가 늘어나면 깨지는 것은 `SseEmitterRegistry` 하나다.** 회원이 A 인스턴스에 붙어
있는데 상태 변경이 B 인스턴스에서 일어나면 신호가 가지 않는다.

깨지지 않는 것도 적어둔다. **티켓은 Redis에 있어서 그대로 동작한다.** 어느 인스턴스에서
발급받아 어느 인스턴스로 구독해도 된다. 그래서 다중화하는 날 할 일은 레지스트리 앞에
pub/sub 한 겹을 얹는 것뿐이고, 발행 지점도 컨트롤러도 프론트엔드도 그대로다.

그날이 오기 전에 미리 만들지 않은 이유는, 지금 만들면 검증할 방법이 없는 코드가 되기
때문이다. 인스턴스가 하나뿐인 환경에서는 pub/sub이 동작하는지 아닌지 구분할 수가 없다.
