# TeenyMoney 퀘스트 기능 전체 인수인계 문서

> 마지막 갱신: 2026-08-10  
> 문서 상태: 퀘스트 제품·API·DB·테스트 설계 확정, GitHub 이슈 분리 완료, `#102` 구현 시작  
> 목적: 이전 대화를 전혀 보지 못한 새 AI 또는 팀원이 이 문서 하나만 읽고 제품 맥락, 결정 이유, 현재 코드 상태, 미결정 사항을 이해하여 설계를 그대로 이어가기 위한 기준 문서

## 0. 새 AI 또는 작업자가 가장 먼저 읽어야 할 내용

이 문서는 단순 회의록이 아니라 퀘스트 기능의 **대화 맥락을 포함한 인수인계 자료**다. 이전 대화에 접근할 수 없다고 가정하고 작성했다.

다음 규칙을 지켜야 한다.

1. `확정`이라고 표시된 정책을 임의로 다시 선택지로 돌리지 않는다.
2. `검토 중`이라고 표시된 항목은 제안일 뿐이므로 사용자에게 확인받은 뒤 확정한다.
3. 와이어프레임, Google Sheets 요구사항, 현재 DB와 이 문서가 충돌하면 이 문서의 확정 사항을 우선한다.
4. 전체 설계는 승인됐으며 현재 `#102 퀘스트 기반 구조 및 생성·조회 API 구현` 단계다. 구현은 이 문서와 단계별 구현 계획을 따른다.
5. 퀘스트와 관계없는 기존 작업 트리 변경을 되돌리거나 덮어쓰지 않는다.
6. 제품의 공식 용어는 반드시 `티니점수`를 사용한다. 과거 자료의 `신뢰도`는 같은 개념을 가리키지만 폐기된 표현이다.

### 0.1 확정 상태의 의미

| 표시 | 의미 |
|---|---|
| 확정 | 사용자와 대화하여 선택을 완료한 정책. 구현 기준으로 사용 |
| 검토 중 | 직전까지 제안했지만 사용자가 아직 최종 승인하지 않은 내용 |
| 보류 | 아이디어는 유효하지만 첫 구현 범위에서는 제외 |
| 현행 | 현재 저장소 또는 기존 요구사항에 실제 존재하는 상태 |

### 0.2 한 문단 요약

TeenyMoney의 퀘스트는 부모가 자녀에게 집안일이나 생활 미션을 제안하고, 자녀가 이를 수락한 뒤 선택적으로 사진이나 글로 인증하며, 부모가 승인하면 부모 지갑에서 자녀 지갑으로 현금 보상이 즉시 이체되는 기능이다. 부모는 티니점수 적용 여부만 선택하고 점수 값은 시스템 정책이 결정한다. 수락한 티니점수 대상 퀘스트를 성공하면 `+3`, 수행하지 못하거나 세 번 반려되어 최종 실패하면 `-2`다. 미수락 만료와 자녀의 명시적 거절에는 감점이 없다. 퀘스트별 상태와 모든 인증 시도는 이력으로 남기고, 이미지는 비공개 S3에 키로 저장하되 업로드 90일 후 삭제한다. 알림과 협동 퀘스트는 후속 기능이다.

## A. 프로젝트와 사용자의 맥락

TeenyMoney는 부모와 자녀가 연결되어 용돈, 금융 활동, 티니점수 등을 관리하는 서비스다. 퀘스트는 단순 할 일 앱이 아니라 다음 세 가지 목적을 함께 가진다.

- 부모가 자녀에게 수행할 일을 명확히 제안한다.
- 자녀가 스스로 수락하거나 거절하고 수행 결과를 인증한다.
- 부모 승인 후 현금 보상과 티니점수 피드백을 일관된 정책으로 반영한다.

사용자 역할은 `PARENT`와 `CHILD`다.

- `PARENT`: 연결된 자녀에게 퀘스트를 만들고, 아직 수락되지 않은 퀘스트를 수정·삭제하며, 제출된 인증을 승인하거나 반려한다.
- `CHILD`: 본인에게 배정된 퀘스트를 수락 또는 거절하고, 수락한 퀘스트의 인증을 제출하거나 재제출하며, 결과와 보상을 확인한다.

이 기능의 우선순위는 **퀘스트 상태와 보상 처리의 정확성**이다. 알림은 유용하지만 현재 대화의 핵심이 아니며 퀘스트 트랜잭션에 결합하지 않는다.

## B. 제공된 와이어프레임을 이미지 없이 이해하기

원본 이미지는 대화 중 임시 경로로 제공되었기 때문에 다른 컴퓨터에서는 존재하지 않을 수 있다. 아래 설명을 화면 설계의 원본 맥락으로 사용한다.

### B.1 자녀용 와이어프레임

자녀 화면은 상단에 `시작 가능`, `진행 중`, `완료` 세 탭이 있다.

1. **시작 가능 탭**
   - 퀘스트 카드에 제목, 간단한 내용, 기한 또는 D-day, 현금 보상, 티니점수 대상 표시가 나온다.
   - 카드를 펼치면 상세 설명과 `퀘스트 수락하기` 버튼을 볼 수 있다.
   - 원본 화면에는 거절 버튼이 없었지만 대화를 통해 명시적 거절 기능을 추가하기로 확정했다.
2. **진행 중 퀘스트의 인증 화면**
   - 제목, 보상, 인증 일시 입력 또는 표시 영역이 있다.
   - 카메라 실행 또는 이미지 업로드 영역과 선택적 상세 글 입력 영역이 있다.
   - 하단의 `퀘스트 인증하기` 버튼으로 제출한다.
3. **진행 중 탭의 상태 목록**
   - 부모 승인을 기다리는 인증은 `승인 대기`로 표시한다.
   - 반려된 퀘스트는 반려 상태, 남은 기회, 재인증 버튼을 표시한다.
   - 제출한 인증을 다시 볼 수 있는 버튼이 있다.
4. **완료 탭**
   - 날짜별로 승인 완료 퀘스트와 성공·실패·만료·거절 결과를 보여준다.
   - 원본에는 성공 퀘스트와 티니점수 증가량 중심으로 표현되어 있었으나, 확정 설계에서는 모든 종료 상태를 포함한다.

### B.2 부모용 와이어프레임

부모 화면도 퀘스트 등록 또는 시작 가능, 진행 중, 완료 탭을 중심으로 구성된다.

1. **퀘스트 목록 화면**
   - 연결된 자녀의 퀘스트 카드가 제목, 보상, 티니점수 정보, 기한과 함께 표시된다.
   - 최근 승인 요청을 상단 강조 카드로 보여주는 아이디어가 포함되어 있다.
   - 퀘스트 생성 화면으로 이동하는 플로팅 버튼이 있다.
2. **퀘스트 생성 화면**
   - 제목, 내용, 기한, 현금 보상, 티니점수 관련 설정을 입력한다.
   - 원본은 부모가 티니점수 수치를 직접 입력하도록 되어 있지만 이 방식은 폐기되었다.
   - 실제 설계에서는 부모가 `티니점수 대상 여부` 체크박스만 선택한다.
   - 원본에는 자녀 선택이 명확하지 않았지만 실제 설계에서는 마지막 단계에서 자녀 1명 이상을 선택한다.
3. **퀘스트 상세 및 수정 화면**
   - 제목, 내용, 기한, 보상을 확인하고 수정·삭제할 수 있다.
   - 실제 정책에서는 `AVAILABLE` 상태일 때만 수정·삭제할 수 있다.
4. **승인 요청 화면**
   - 자녀 정보, 퀘스트 정보, 현금 보상, 기한, 인증 사진, 자녀의 인증 글을 보여준다.
   - 하단에 요청 거절과 요청 수락 버튼이 있다.
   - 실제 설계에서는 반려 사유를 선택적으로 받고, 기한 후 반려라면 연장 또는 최종 실패를 선택하게 한다.

와이어프레임의 시각 스타일은 참고 대상이지만 현재 대화에서는 UI 픽셀 구현보다 도메인 정책을 먼저 확정하고 있다.

## C. 요구사항 명세서에 원래 있던 내용

Google Sheets에는 `자녀`, `부모`, `참고`, `예상 화면 used AI`, `확장기능 의논` 탭이 있다. 기존 요구사항에서 확인한 퀘스트 관련 핵심은 다음과 같다.

### C.1 자녀 요구사항

- 퀘스트의 기한, 내용, 보상을 확인하고 수락한다.
- 사진과 글을 이용해 수행 결과를 인증한다.
- 부모 승인 상태를 확인한다.
- 반려 후 최대 3회까지 다시 제출한다.
- 현금과 점수 보상을 확인한다.
- 시작 가능, 진행 중, 완료 탭을 사용한다.
- 완료 결과에 성공과 실패가 존재한다.

### C.2 부모 요구사항

- 제목, 내용, 기한, 보상 금액을 입력해 퀘스트를 생성한다.
- 상태별 탭에서 퀘스트를 조회한다.
- 자녀가 수락하기 전까지만 수정·삭제한다.
- 최신 인증 요청을 확인한다.
- 승인하면 보상을 이체한다.
- 잔액이 부족하면 안내한다.
- 반려할 때 남은 제출 횟수를 감소시키며 최대 3회를 허용한다.

### C.3 명세서에 없거나 불충분했던 내용

다음은 기존 명세서에 명확히 정의되어 있지 않아 이번 대화에서 새로 설계했다.

- 부모가 티니점수 숫자를 직접 입력할지 여부
- 퀘스트 성공·실패 점수표와 월간 상·하한
- 점수와 등급이 실시간인지 월간인지
- 보상 송금과 완료 처리의 정확한 순서 및 트랜잭션
- 잔액 부족 시 퀘스트 상태
- 자녀의 명시적 거절과 거절 사유
- 미수락 상태로 기한이 지난 퀘스트의 상태와 감점 여부
- 기한 내 제출 후 기한이 지나 반려된 경우의 재시도 처리
- 사진과 글의 필수 조합
- 여러 자녀 선택과 생성 원자성
- 협동 퀘스트 여부
- 완료 이력과 이미지 보관 기간
- S3에 URL이 아닌 키를 저장하는 정책
- 알림 기술과 수동 확인 요청 제한
- 인증 시도별 이력 보존 방식

## D. 대화에서 선택한 방향과 그 이유

이 장은 숫자로만 오갔던 `1번`, `2번`, `3번` 선택의 의미를 복원하기 위한 결정 이력이다.

### D.1 수락형 시작을 먼저 구현 — 확정

비교한 방향은 자녀가 직접 수락해야 시작하는 방식과, 부모가 만들면 자동으로 진행 상태가 되는 방식이었다.

선택한 방향은 **자녀가 직접 수락하는 방식**이다.

이유:

- 실패 시 티니점수를 감점하려면 자녀가 수행 의사를 명시한 퀘스트에만 책임을 부여하는 것이 공정하다.
- 부모가 일방적으로 만든 미션 때문에 자녀 점수가 내려가는 문제를 막는다.
- 수락 전 수정·삭제 가능, 수락 후 수정 불가라는 상태 규칙이 명확해진다.
- 자동 시작은 반복 퀘스트 같은 후속 기능에서 별도 검토할 수 있다.

### D.2 부모 점수 직접 입력 폐기 — 확정

초기 화면에는 부모가 점수를 직접 입력하는 필드가 있었지만 사용하지 않기로 했다. 부모는 티니점수 적용 여부만 체크한다.

이유:

- 가정마다 점수 가치가 달라지는 것을 막는다.
- 과도한 보상·감점과 부모의 감정적 점수 설정을 제한한다.
- 금융 기능 전반에서 티니점수의 의미를 일관되게 유지한다.
- 운영 중 정책 수치만 조정할 수 있어 데이터 비교와 유지보수가 쉽다.

단점은 퀘스트 난이도 차이를 세밀하게 반영하기 어렵다는 점이다. 첫 버전에서는 단순성과 공정성을 우선하고, 난이도별 점수는 데이터가 쌓인 뒤 재검토한다.

### D.3 점수는 실시간, 등급은 월간 고정 — 확정

점수와 등급을 모두 실시간으로 바꾸는 안과 월 단위로만 보여주는 안을 비교했다. 최종적으로 둘을 분리했다.

- 티니점수는 행동 직후 실시간 반영하여 피드백을 준다.
- 등급과 등급 혜택은 매월 1일 00:00(한국 서버 시간)에 당시 점수를 기준으로 새로 확정하고, 그 달 동안 유지한다.
- 신규 가입자는 가입 시점의 점수를 기준으로 최초 등급을 바로 부여하고, 이후부터 월간 갱신 주기를 따른다.
- 이미 가입한 예금·대출 등 금융상품에 저장된 적용 금리는 등급이 바뀌어도 다시 계산하지 않는다.

이렇게 하면 자녀는 행동 결과를 바로 확인하면서도, 금융 우대나 등급이 하루에도 여러 번 바뀌는 혼란을 피할 수 있다.

### D.4 승인 시 송금, 송금 성공과 완료를 원자적으로 처리 — 확정

보상을 생성 시 예약하는 방식, 성공부터 기록한 후 송금하는 방식, 승인 트랜잭션 안에서 송금과 완료를 함께 처리하는 방식을 비교했다.

선택한 방향은 **부모 승인 시 실제 송금하고, 송금과 완료를 하나의 트랜잭션으로 처리하는 방식**이다.

이유:

- 첫 버전에서 잔액 예약 시스템을 새로 만드는 복잡성을 피한다.
- 완료됐지만 돈을 못 받은 상태나 돈을 받았지만 퀘스트가 미완료인 상태를 막는다.
- 잔액 부족 시 `PENDING`을 유지하면 부모가 충전 후 다시 승인할 수 있다.

### D.5 완료 데이터와 이미지의 보관을 분리 — 확정

모든 완료 퀘스트를 UI에 한 번에 계속 쌓는 방식은 성능과 사용성 문제가 있다. 반대로 조기 삭제하면 분쟁이나 회고가 어렵다.

선택한 방향:

- 퀘스트와 텍스트 이력은 계정 생명주기 동안 보관한다.
- 화면은 커서 페이지네이션으로 최근 데이터부터 20개씩 보여준다.
- 용량이 큰 이미지만 S3 Lifecycle로 업로드 90일 후 삭제한다.

### D.6 기한 후 반려는 연장 또는 최종 실패 — 확정

기한이 지난 인증을 단순히 재시도 불가로 만드는 안, 부모가 항상 연장할 수 있게 하는 안, 부모에게 선택권을 주는 절충안을 비교했다.

선택한 방향은 다음과 같다.

- 기한 전에 제출된 `PENDING` 인증은 기한이 지나도 살아 있다.
- 그 인증을 부모가 늦게 반려하면 `기한 연장 후 재시도` 또는 `최종 실패`를 선택한다.
- 세 번째 반려에서는 무조건 최종 실패한다.

이 방식은 부모의 늦은 확인 때문에 자녀가 자동 실패하는 것을 막으면서도, 이미 지난 기한을 무제한으로 무시하지 않는다.

### D.7 여러 자녀 배정은 독립 퀘스트 생성 — 확정

부모는 한 번의 입력으로 여러 자녀를 선택할 수 있지만, DB에는 자녀마다 독립 행을 만든다.

이유:

- 각 자녀가 서로 다른 시점에 수락·거절·성공·실패할 수 있다.
- 한 자녀의 승인이나 보상 실패가 다른 자녀의 상태에 영향을 주지 않는다.
- 현재 스키마와 단일 자녀 상태 모델을 복잡하게 확장하지 않아도 된다.

### D.8 협동 퀘스트는 별도 후속 모델 — 보류

여러 자녀가 힘을 합쳐 하나의 퀘스트를 완료하는 아이디어는 유용하지만 첫 버전에 넣지 않는다.

협동 퀘스트는 공동 성공 조건, 일부 참여자의 미수행, 보상 분배, 공동 인증, 감점 책임 등 별도 정책이 필요하다. 나중에 필요할 때 현재 테이블에 조건문을 쌓지 않고 팀 퀘스트 모델로 따로 설계한다.

### D.9 인증은 유연하되 부모가 필수 방식을 선택 — 확정

사진과 글은 모두 선택 사항일 수 있고 둘 다 생략할 수도 있다. 다만 부모가 퀘스트 성격에 따라 최소 인증 방식을 정할 수 있게 한다.

첫 버전은 `FREE`, `PHOTO_REQUIRED`, `TEXT_REQUIRED`, `ANY_REQUIRED` 네 가지만 제공한다. 사진과 글을 무조건 모두 요구하는 `BOTH_REQUIRED`는 필요성이 확인될 때 추가한다.

### D.10 자녀 거절과 사유 축적 — 확정, 분석은 보류

원래 화면에는 수락만 있었지만 자녀에게 거절 버튼을 제공하기로 했다.

이유:

- 수락하지 않을 권리를 명시적으로 제공한다.
- 기한 만료와 의도적 거절을 구분할 수 있다.
- 부모는 퀘스트가 거절된 이유를 보고 난이도나 보상을 조정할 수 있다.
- 향후 소비 리포트나 가족 리포트의 참고 데이터로 사용할 수 있다.

단, 거절 데이터를 점수화하거나 자녀를 압박하는 지표로 만들지는 않는다.

### D.11 인증은 시도별로 모두 보관 — 확정

인증을 같은 행에 덮어쓰지 않고 매 제출마다 새 행을 삽입한다.

이유:

- 어떤 인증이 왜 반려됐는지 추적할 수 있다.
- 남은 기회 계산과 부모·자녀 간 분쟁 확인이 쉽다.
- 현재 DB도 `quest_id`에 유일 제약이 없어 1:N 저장이 가능한 구조다.

### D.12 상태 중심 서비스 구조 — 확정

단일 `QuestService`에 모든 로직을 넣는 방식과 범용 워크플로 엔진을 만드는 방식을 피하고, 생성·진행·검토·마감 책임을 분리한다.

이유:

- 승인 트랜잭션과 인증 제출, 배치 마감의 책임이 다르다.
- 상태 전이 규칙은 하나의 정책 객체에서 재사용할 수 있다.
- 현재 Spring MVC/MyBatis 구조에서 과도한 추상화 없이 테스트하기 쉽다.

## E. 구현에서 절대 깨면 안 되는 도메인 불변식

아래 규칙은 API 모양과 관계없이 반드시 지켜야 한다.

1. 부모는 연결된 본인 자녀의 퀘스트만 생성·조회·수정·삭제·검토할 수 있다.
2. 자녀는 본인에게 배정된 퀘스트만 조회·수락·거절·인증할 수 있다.
3. 부모는 티니점수 값을 직접 정할 수 없다.
4. 자녀가 수락하지 않은 퀘스트로는 티니점수를 차감할 수 없다.
5. `AVAILABLE` 상태에서만 부모 수정·삭제, 자녀 수락·거절이 가능하다.
6. `IN_PROGRESS`에서만 새 인증 제출을 시작할 수 있다.
7. 한 퀘스트에는 동시에 하나의 `PENDING` 인증만 존재한다.
8. 인증 시도는 수정 또는 덮어쓰지 않고 새 이력으로 추가한다.
9. 부모는 최신 `PENDING` 인증만 승인하거나 반려할 수 있다.
10. 승인 시 지갑 차감·적립·원장·점수·인증·퀘스트 상태를 한 트랜잭션으로 처리한다.
11. 승인 트랜잭션 실패 시 퀘스트와 인증은 `PENDING`을 유지한다.
12. 동일 퀘스트의 현금 보상과 점수 이벤트는 중복 반영할 수 없다.
13. 기한 내 제출된 `PENDING` 인증은 부모 검토가 늦어져도 자동 실패하지 않는다.
14. 세 번째 반려는 기한과 관계없이 최종 실패다.
15. 종료 상태에서는 추가 상태 전이를 허용하지 않는다.
16. S3 presigned URL을 DB에 저장하지 않고 객체 키만 저장한다.
17. 알림 실패는 퀘스트 트랜잭션을 실패시키지 않는다.

## F. 대표 사용자 시나리오

### F.1 현금과 티니점수가 있는 정상 성공

1. 부모가 현금 2,000원, 티니점수 대상, 사진 필수인 퀘스트를 자녀 A에게 만든다.
2. 퀘스트는 `AVAILABLE`이다.
3. 자녀 A가 수락하면 `IN_PROGRESS`가 된다.
4. 자녀 A가 기한 내 사진과 선택적 글을 제출하면 인증 행 1번이 생기고 퀘스트는 `PENDING`이 된다.
5. 부모가 승인한다.
6. 부모 지갑에서 2,000원을 차감하고 자녀 지갑에 2,000원을 적립한다.
7. 원장 기록과 티니점수 `+3`을 반영한다.
8. 인증은 `APPROVED`, 퀘스트는 `COMPLETED`가 된다.

### F.2 부모 잔액 부족

1. 자녀가 정상 인증을 제출해 퀘스트가 `PENDING`이다.
2. 부모가 승인하지만 잔액이 부족하다.
3. 송금, 점수, 인증 상태, 퀘스트 상태 중 어느 것도 변경하지 않는다.
4. 부모에게 잔액 부족을 안내하고 퀘스트는 계속 `PENDING`이다.
5. 부모가 충전 후 다시 승인할 수 있다.

### F.3 수락 후 인증하지 못한 실패

1. 티니점수 대상 퀘스트를 자녀가 수락해 `IN_PROGRESS`가 된다.
2. 기한까지 인증하지 않는다.
3. 퀘스트는 `FAILED`가 되고 티니점수 `-2`를 한 번 반영한다.

### F.4 미수락 만료

1. 퀘스트가 `AVAILABLE`인 채 기한이 지난다.
2. `EXPIRED`로 종료한다.
3. 자녀가 수행 의사를 밝힌 적이 없으므로 티니점수는 차감하지 않는다.

### F.5 명시적 거절

1. 자녀가 `AVAILABLE` 퀘스트에서 거절 사유를 선택한다.
2. 퀘스트는 `DECLINED`가 된다.
3. 감점하지 않는다.
4. 부모는 사유를 확인할 수 있고 데이터는 후속 분석을 위해 보관한다.

### F.6 기한 후 첫 번째 반려와 연장

1. 자녀가 기한 전에 인증을 제출해 `PENDING`이 된다.
2. 부모가 기한이 지난 뒤 인증을 확인하고 반려한다.
3. 시스템은 추가 시도 기간이 지났음을 알리고 연장 여부를 묻는다.
4. 부모가 새 기한을 선택하고, 필요하면 반려 사유를 입력한다.
5. 남은 기회가 3에서 2로 감소하고 퀘스트는 `IN_PROGRESS`가 된다.
6. 자녀가 새 기한 안에 인증을 다시 제출하면 새 인증 행 2번이 생긴다.

### F.7 세 번 반려된 최종 실패

1. 부모가 각 인증을 반려하고, 필요하면 사유를 입력한다.
2. 인증 행은 모두 보관되고 남은 기회는 반려마다 감소한다.
3. 세 번째 반려에서 남은 기회가 0이 되며 퀘스트는 `FAILED`가 된다.
4. 티니점수 대상이라면 `-2`를 한 번만 반영한다.

## G. 하지 않기로 한 잘못된 해석

새 작업자가 아래와 같이 구현하면 합의와 어긋난다.

- 부모가 퀘스트마다 `+5`, `+10`처럼 점수를 직접 입력하게 만드는 것
- 퀘스트 생성 시 보상 금액을 부모 지갑에서 미리 차감하거나 예약하는 것
- 돈 송금 실패와 관계없이 먼저 `COMPLETED`로 바꾸는 것
- 자녀가 수락하지 않은 퀘스트 만료에 감점을 주는 것
- 부모의 검토가 늦었다는 이유로 기한 내 제출된 `PENDING` 인증을 실패시키는 것
- 재인증 시 이전 인증 사진, 글, 반려 사유를 덮어쓰는 것
- 인증 이미지의 presigned URL을 DB에 저장하는 것
- 완료 탭에서 종료 데이터를 전부 한 번에 내려주는 것
- 알림 발송을 승인 트랜잭션 안에서 동기 호출하는 것
- 첫 버전부터 협동 퀘스트나 범용 워크플로 엔진을 함께 구현하는 것
- 거절 횟수를 티니점수 감점이나 자녀 순위에 사용하는 것

## 3. 용어와 핵심 방향

- 정식 명칭은 **티니점수**다. `신뢰도`, `신뢰도 점수`라는 표현은 사용하지 않는다.
- 퀘스트는 부모가 생성하고 자녀가 직접 수락한 뒤 수행한다.
- 자동 시작 방식은 현재 범위에서 제외한다.
- 현금 보상과 티니점수 보상은 서로 독립적으로 선택할 수 있다.
- 현재 버전은 자녀 한 명당 독립 퀘스트 한 건을 만드는 구조다.
- 알림, 협동 퀘스트, 소비 리포트 분석은 현재 핵심 구현 범위가 아니다.

## 4. 퀘스트 생성

부모가 입력하는 항목은 다음과 같다.

- 제목
- 상세 내용
- 최종 기한
- 현금 보상 금액
- 티니점수 대상 여부 체크박스
- 인증 필수 방식
- 퀘스트를 받을 자녀 1명 이상

### 4.1 보상 유효성

아래 조건 중 하나 이상을 만족해야 생성할 수 있다.

```text
rewardAmount > 0
OR
teenyScoreEnabled == true
```

따라서 다음 조합이 가능하다.

- 현금만 지급
- 티니점수만 반영하고 현금은 0원
- 현금과 티니점수 모두 적용

현금과 티니점수가 모두 없는 퀘스트는 허용하지 않는다.

현금 보상에 제품 정책상의 별도 상한은 두지 않지만, DB `BIGINT`와 Java `Long` 범위를 벗어나거나 여러 자녀의 총 예상 보상 계산에서 숫자 범위를 넘는 요청은 `400 QUEST_REWARD_INVALID`로 거절한다.

### 4.2 여러 자녀 선택

- 퀘스트 내용을 먼저 작성한 뒤 연결된 자녀를 1명 이상 선택한다.
- 선택한 자녀마다 독립된 퀘스트 행을 생성한다.
- 생성은 하나의 트랜잭션으로 처리한다.
- 자녀 한 명에 대한 생성이라도 실패하면 전체 생성을 롤백한다.
- 생성 이후 각 자녀의 수락, 인증, 보상, 성공 및 실패 상태는 서로 영향을 주지 않는다.
- 별도의 배치 또는 그룹 테이블은 만들지 않는다.

### 4.3 수정과 삭제

- 부모는 `AVAILABLE` 상태에서만 퀘스트를 수정하거나 삭제할 수 있다.
- 자녀가 수락한 이후에는 수정하거나 삭제할 수 없다.
- `AVAILABLE` 상태에서 부모가 삭제한 퀘스트는 물리 삭제하며 완료 이력에 남기지 않는다.

## 5. 인증 방식

부모는 퀘스트 생성 시 아래 네 가지 중 하나를 선택한다.

| 값 | 의미 |
|---|---|
| `FREE` | 사진과 글 모두 선택 사항이며, 둘 다 없어도 제출 가능 |
| `PHOTO_REQUIRED` | 사진 필수, 글 선택 |
| `TEXT_REQUIRED` | 글 필수, 사진 선택 |
| `ANY_REQUIRED` | 사진 또는 글 중 하나 이상 필수 |

- `BOTH_REQUIRED`는 첫 버전에서 제공하지 않는다.
- 인증 방식은 자녀가 수락하기 전에 확인할 수 있어야 한다.
- 자녀가 수락한 뒤에는 인증 방식을 변경할 수 없다.

## 6. 상태 모델

퀘스트 상태는 다음 일곱 가지로 확정한다.

| 상태 | 의미 | 화면 탭 |
|---|---|---|
| `AVAILABLE` | 자녀가 아직 수락하거나 거절하지 않음 | 시작 가능 |
| `IN_PROGRESS` | 자녀가 수락했고 인증을 준비 중 | 진행 중 |
| `PENDING` | 인증을 제출했고 부모의 확인을 기다림 | 진행 중 |
| `COMPLETED` | 부모가 승인하고 보상 지급까지 완료 | 완료 |
| `FAILED` | 기한 미수행 또는 최종 반려로 실패 | 완료 |
| `EXPIRED` | 자녀가 수락하지 않은 채 기한 만료 | 완료 |
| `DECLINED` | 자녀가 명시적으로 거절 | 완료 |

### 6.1 상태 전이

```text
AVAILABLE --수락--> IN_PROGRESS
AVAILABLE --자녀 거절--> DECLINED
AVAILABLE --기한 만료--> EXPIRED

IN_PROGRESS --기한 내 인증 제출--> PENDING
IN_PROGRESS --인증 없이 기한 만료--> FAILED

PENDING --부모 승인 및 보상 지급--> COMPLETED
PENDING --재시도 가능한 반려--> IN_PROGRESS
PENDING --세 번째 반려--> FAILED
PENDING --기한 후 최종 실패 선택--> FAILED
```

- 종료 상태인 `COMPLETED`, `FAILED`, `EXPIRED`, `DECLINED`에서는 다른 상태로 전이할 수 없다.
- 종료 상태로 바꾸는 트랜잭션에서 서버 현재 시각을 `ended_at`에 함께 기록하며, 네 종료 상태의 `ended_at`은 항상 값이 있어야 한다.
- 한 퀘스트에는 동시에 하나의 `PENDING` 인증만 존재할 수 있다.
- 자녀가 기한 전에 인증을 제출했다면 부모가 기한 후에 확인하더라도 자동 실패하지 않는다.

## 7. 자녀의 퀘스트 거절

- 자녀는 `AVAILABLE` 상태에서 퀘스트를 거절할 수 있다.
- 거절해도 티니점수를 차감하지 않는다.
- 거절 사유 코드는 필수이고 상세 설명은 선택 사항이다.
- `OTHER`를 선택하면 상세 설명이 필수다.

거절 사유 코드는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `NOT_ENOUGH_TIME` | 시간이 부족함 |
| `TOO_DIFFICULT` | 너무 어려움 |
| `REWARD_NOT_ENOUGH` | 보상이 부족함 |
| `HARD_TO_VERIFY` | 인증하기 어려움 |
| `CANNOT_DO_NOW` | 지금은 수행할 수 없음 |
| `OTHER` | 기타 |

- 부모는 퀘스트별 거절 사유를 확인할 수 있다.
- 거절 데이터를 향후 소비 리포트 등에 사용할 수 있도록 보관한다.
- 현재 버전에서는 거절 통계나 분석 화면을 만들지 않는다.
- 거절 횟수로 자녀를 평가하거나 티니점수를 조정하지 않는다.

## 8. 인증 제출과 반려

- 최초 남은 인증 기회는 3회다.
- 부모가 반려할 때마다 남은 기회를 `3 → 2 → 1 → 0`으로 감소시킨다.
- 반려 사유는 선택 사항이다.
- 첫 번째와 두 번째 반려는 조건에 따라 재인증할 수 있다.
- 세 번째 반려는 항상 최종 실패다.
- 인증 이력은 덮어쓰지 않고 시도마다 새 행으로 저장한다.
- 최신 인증은 `attempt_no`가 가장 큰 행이다.
- 승인한 인증은 `APPROVED`, 반려한 인증은 `REJECTED`로 바꾸고 `reviewed_at`을 서버 시간으로 기록한다.
- 기한 미수행 또는 부모의 최종 실패 선택으로 퀘스트가 `FAILED`가 되면 `remaining_count`를 0으로 만든다.

### 8.1 기한이 지난 뒤의 반려

자녀가 기한 내 인증을 제출했지만 부모가 기한이 지난 후 반려하려는 경우 다음 안내를 표시한다.

> 현재 자녀가 해당 퀘스트를 추가 시도할 수 있는 기간이 지났습니다. 기한을 연장하시겠습니까?

부모는 아래 중 하나를 선택한다.

1. 새 날짜와 시간을 지정해 기한을 연장하고 반려한다.
   - 반려 사유 선택
   - 남은 기회 1회 차감
   - 퀘스트를 `IN_PROGRESS`로 전환
2. 기한을 연장하지 않고 최종 실패 처리한다.
   - 퀘스트를 `FAILED`로 전환
   - 티니점수 대상 퀘스트라면 실패 점수 반영

세 번째 반려에서는 연장 선택지를 제공하지 않는다.

## 9. 현금 보상과 승인

현금은 퀘스트를 만들거나 자녀가 수락할 때 예약하지 않는다. 부모가 인증을 승인하는 시점에 송금한다.

승인 작업은 다음 전체 과정을 하나의 DB 트랜잭션으로 처리한다.

```text
퀘스트 및 최신 인증 검증·잠금
→ 부모 잔액 확인
→ 부모 지갑 차감
→ 자녀 지갑 적립
→ 지갑 원장 기록
→ 티니점수 성공 반영
→ 인증 승인 처리
→ 퀘스트 완료 처리
→ 커밋
```

- 어느 단계에서든 실패하면 전체 작업을 롤백한다.
- 현금 보상이 0원이면 부모·자녀 지갑 조회와 송금·원장 기록을 건너뛰고 티니점수 및 상태만 같은 트랜잭션에서 처리한다.
- 부모 잔액이 부족하면 돈과 티니점수를 변경하지 않는다.
- 잔액 부족 시 인증과 퀘스트는 `PENDING` 상태를 유지해 부모가 다시 승인할 수 있게 한다.
- 퀘스트를 먼저 성공 처리한 뒤 별도로 송금하는 방식은 사용하지 않는다.

## 10. 티니점수 정책

부모는 점수 값을 직접 입력할 수 없다. 부모가 설정할 수 있는 것은 해당 퀘스트를 티니점수 대상에 포함할지 여부뿐이다.

점수 값은 시스템 정책으로 관리한다.

| 이벤트 | 점수 |
|---|---:|
| 티니점수 대상 퀘스트 성공 | `+3` |
| 수락한 퀘스트를 인증하지 못하고 기한 만료 | `-2` |
| 세 번 반려되어 최종 실패 | `-2` |
| 기한 후 부모가 최종 실패 선택 | `-2` |
| 수락하지 않은 퀘스트 만료 | `0` |
| 자녀가 퀘스트 거절 | `0` |

### 10.1 월간 상·하한은 구현하지 않는다 — 2026-08-12 변경

초안은 월간 합계 상한 `+20`, 하한 `-10`을 두기로 했으나 **#104에서 범위 밖으로 정리했고 구현하지 않았다.**
현재는 성공마다 `+3`, 최종 실패마다 `-2`가 상한 없이 누적된다. `TeenyScoreChangeService`의
0~1000 절대 범위 보정만 적용된다.

이 결정은 마감 배치(#105)에도 그대로 적용된다. 한 달에 자동 실패가 여러 건 나면 감점이
그만큼 누적된다. 상한이 필요하다고 판단되면 별도 이슈로 다루고, 그때 퀘스트 이벤트만
집계하는 월간 합계 조회가 함께 필요하다.

### 10.2 점수 이벤트 코드

| 코드 | 점수 | 발생 |
|---|---:|---|
| `QUEST_COMPLETED` | `+3` | 부모 승인 |
| `QUEST_FAILED` | `-2` | 3회 반려 최종 실패, 기한 후 최종 실패 선택, 수락 후 미수행 마감 |

초안은 실패를 `QUEST_FAILED_DEADLINE`과 `QUEST_FAILED_REJECTED`로 나누려 했으나
**`QUEST_FAILED` 하나로 통합했다.** 원인별로 키가 나뉘면 반려로 실패한 퀘스트를 마감 배치가
다시 감점해 `-4`가 될 수 있는데, 키가 하나면 이벤트 키 중복 방지가 그것까지 막는다.

실패 원인은 이력에 남지 않는다. 필요하면 `reference_type = 'QUEST'`, `reference_id = questId`로
퀘스트를 찾아 최종 상태에서 추론한다.

중복 점수 반영은 퀘스트 ID 기반 이벤트 키(`QUEST_COMPLETED:{questId}`, `QUEST_FAILED:{questId}`)로
방지한다.

## 11. 티니점수와 등급 표시

- 티니점수는 이벤트가 발생한 즉시 변경하고 이력을 기록한다.
- 점수는 월이 바뀌어도 초기화하지 않는다.
- 등급과 등급 혜택은 매월 1일 00:00(한국 서버 시간)에 당시 점수를 기준으로 새로 확정한다.
- 한 번 확정된 이달의 등급은 그 달 동안 고정한다.
- 월중 점수가 오르거나 내려도 다음 달 1일 전까지 현재 등급과 혜택은 바뀌지 않는다.
- 신규 가입자는 가입 시점의 점수를 기준으로 최초 등급을 즉시 부여하고, 다음 달부터 같은 월간 갱신 주기를 적용한다.
- 이미 가입한 금융상품에 저장된 적용 금리는 이후 등급 변경의 영향을 받지 않는다.

현재 코드의 등급 구간은 다음과 같다.

| 등급 | 점수 범위 | 금리 보너스 | 부모 승인 예외 횟수 |
|---|---:|---:|---:|
| 회복필요 | 0~199 | 0% | 0 |
| 주의 | 200~399 | 0% | 1 |
| 보통 | 400~599 | 10% | 2 |
| 양호 | 600~799 | 20% | 3 |
| 우수 | 800~1000 | 30% | 5 |

현재 구현은 실시간 점수로 등급까지 즉시 계산하므로 월간 등급 스냅샷 기능은 새로 구현해야 한다.

## 12. 완료 이력과 이미지 보관

- 퀘스트 메타데이터와 텍스트 인증 이력은 계정이 유지되는 동안 보관한다.
- 완료 탭에는 `COMPLETED`, `FAILED`, `EXPIRED`, `DECLINED`를 표시한다.
- 완료 탭은 최신순 커서 페이지네이션을 사용한다.
- 기본 조회 개수는 20개다.
- 인증 이미지는 비공개 S3 버킷에 저장한다.
- DB에는 공개 URL이 아니라 S3 객체 키만 저장한다.
- 조회 시 짧은 만료 시간을 가진 presigned URL을 발급한다.
- S3 키 prefix는 `quest-verifications/{questId}/...`를 사용한다.
- S3 Lifecycle로 업로드 시점부터 90일 뒤 이미지를 자동 삭제한다.
- 이미지가 삭제된 뒤에도 인증 텍스트, 상태, 시각, 반려 사유는 유지한다.
- UI에는 `이미지 보관 기간이 만료되었습니다`와 같은 안내를 표시한다.

## 13. 알림

알림은 퀘스트 핵심 구현에서 분리한다.

- 향후 `Firebase Cloud Messaging + PWA` 방식으로 구현할 가능성이 높다.
- 자녀의 수동 확인 요청 버튼도 알림 기능을 구현할 때 함께 추가한다.
- 권장 제한은 동일 퀘스트 기준 12시간 쿨다운, 24시간 최대 2회다.
- 알림 발송 실패가 퀘스트 상태 변경이나 보상 지급을 롤백해서는 안 된다.

현재 퀘스트 기능에는 아래 이벤트 훅만 고려한다.

- 인증 제출
- 확인 요청
- 승인
- 반려
- 기한 임박 및 만료
- 보상 지급 실패

## 14. 구현 구조와 DB 변경 방향 — 확정

### 14.1 서비스 구조

하나의 거대한 서비스나 범용 워크플로 엔진을 만들지 않고, 상태 중심 도메인 서비스로 분리한다.

- `QuestCreationService`: 일괄 생성, 수정, 삭제
- `QuestProgressService`: 수락, 거절, 인증 제출 및 재제출
- `QuestReviewService`: 승인, 반려, 연장 후 반려, 최종 실패
- `QuestDeadlineService`: 미수락 만료 및 미수행 실패
- `QuestQueryService`: 역할별 조회 범위, 탭, 커서 목록과 상세 조회
- `QuestStatePolicy`: 허용 상태 전이 검증

기존 프로젝트 구조에 맞춰 `controller`, `dto/request`, `dto/response`, `service`, `mapper`, `vo`를 사용하고 응답은 `ApiResponse<T>`, 예상 가능한 오류는 `BusinessException`과 도메인 `ErrorCode`로 처리한다.

### 14.2 `T_QST_BASE_M`

현재 마이그레이션이 `V011`까지 존재하므로 적용할 마이그레이션 이름은 `V012__extend_quest_domain.sql`이다.

- 부모가 점수를 입력하지 않으므로 `reward_teeny_score` 제거
- 티니점수 대상 여부인 `is_teeny_score` 유지
- `verification_requirement` 추가
- `decline_reason_code` 추가
- `decline_reason_detail` 추가
- `completed_at`을 종료 상태 전반에 맞는 `ended_at`으로 변경
- 상태 제약에 `EXPIRED`, `DECLINED` 추가
- `remaining_count` 기본값을 3으로 설정
- `deadline`은 현재 유효 기한으로 사용하고, 늦은 반려 후 연장하는 경우에만 갱신
- UUID를 저장하는 `creation_request_key CHAR(36)` 추가
- `(parent_id, creation_request_key, child_id)` 유일 제약 추가
- 마감 조회용 `(status, deadline, id)` 인덱스 추가
- 자녀별 독립 행을 만들며 별도 배치 테이블은 추가하지 않음

### 14.3 `T_QST_VERIFY_L`

현재 테이블은 `quest_id`가 유일하지 않아 이미 한 퀘스트에 여러 인증 이력을 저장할 수 있다. 구현 시 기존 행을 갱신하지 않고 매 시도마다 새 행을 삽입한다.

- `image_url`을 `image_key`로 변경
- `attempt_no` 추가 및 필수값 설정
- `(quest_id, attempt_no)` 유일 제약 추가
- 기존 데이터가 있으면 `created_at`, `id` 순으로 시도 번호를 채운 뒤 제약 추가
- 인증 상태는 기존 값을 유지
- 반려 시 `rejection_reason`은 선택 사항이며, 값이 있으면 공백 제거 후 1~500자
- 최신 인증은 `ORDER BY attempt_no DESC LIMIT 1`로 조회

### 14.4 마이그레이션 전 확인 사항

- 현재 마이그레이션 번호는 `V001`부터 `V011`까지 중복 없이 존재한다. 퀘스트 변경은 다음 번호인 `V012`를 사용한다.
- 변경한 스키마는 기준 스키마와 로컬 seed에도 동기화해야 한다.
- 기존 프로필 이미지는 이미 S3 키 저장 방식으로 전환했지만 퀘스트 인증 이미지는 아직 URL 방식이므로 마이그레이션이 필요하다.

## 15. API 및 트랜잭션 설계 — 확정

아래 경로는 모두 `/api/v1` 아래에 둔다.

### 15.1 API

| 역할 | 메서드와 경로 | 기능 |
|---|---|---|
| 공통 | `GET /quests?tab=AVAILABLE\|ONGOING\|COMPLETED` | 역할에 맞는 탭별 목록 조회 |
| 공통 | `GET /quests/{questId}` | 상세 조회 |
| 부모 | `POST /quests` | 선택한 여러 자녀에게 독립 퀘스트 일괄 생성 |
| 부모 | `PATCH /quests/{questId}` | `AVAILABLE` 퀘스트 수정 |
| 부모 | `DELETE /quests/{questId}` | `AVAILABLE` 퀘스트 삭제 |
| 자녀 | `PATCH /quests/{questId}/accept` | 수락 |
| 자녀 | `PATCH /quests/{questId}/decline` | 사유와 함께 거절 |
| 자녀 | `POST /quests/{questId}/verifications` | 사진 및 글 인증 제출 |
| 부모 | `PATCH /quests/{questId}/verifications/{verificationId}/approve` | 승인 및 보상 지급 |
| 부모 | `PATCH /quests/{questId}/verifications/{verificationId}/reject` | 반려, 연장 또는 최종 실패 |

- 부모는 목록에서 `childId`로 자녀를 필터링할 수 있다.
- 자녀가 `childId`를 보내면 무시하지 않고 `400`으로 응답한다.
- `AVAILABLE` 탭은 `AVAILABLE`, `ONGOING` 탭은 `IN_PROGRESS`와 `PENDING`, `COMPLETED` 탭은 `COMPLETED`, `FAILED`, `EXPIRED`, `DECLINED`를 조회한다.
- 시작 가능·진행 중 탭은 `(deadline ASC, questId ASC)`, 완료 탭은 `(endedAt DESC, questId DESC)` 기반 커서를 사용한다.
- 인증 제출은 `multipart/form-data`를 사용하고 이미지와 글은 인증 방식에 따라 검증한다.
- `POST /quests`는 필수 헤더 `X-Creation-Request-Key`로 UUID를 받는다. 프론트는 사용자가 생성 버튼을 누른 한 번의 생성 작업마다 새 UUID를 만들고, 같은 네트워크 재요청에서만 같은 값을 다시 사용한다.
- 다른 상태 변경 API에는 요청 식별 키를 받지 않는다.

### 15.2 동시성과 트랜잭션

- 모든 상태 변경 전에 퀘스트 행을 `SELECT ... FOR UPDATE`로 잠근다.
- 잠금 뒤 현재 사용자 권한, 상태, 기한, 최신 인증 여부를 다시 검증한다.
- 기한이 지난 `AVAILABLE` 퀘스트의 수정·삭제·수락·거절과 기한이 지난 `IN_PROGRESS` 퀘스트의 인증 제출은 `409 QUEST_DEADLINE_PASSED`로 거절하고 상태를 직접 바꾸지 않는다. 마감 상태 변경은 스케줄러가 담당한다.
- 서버 시간이 기한과 정확히 같은 초라면 해당 명령을 허용한다. 기한 내 제출된 `PENDING` 인증의 승인·반려는 기한 경과로 막지 않는다.
- 일괄 생성은 부모 회원 행을 먼저 잠가 같은 부모의 생성 요청을 순서대로 처리한다. 그 뒤 기존 `creation_request_key`의 내용과 전체 자녀 집합을 비교하여, 서로 다른 자녀 집합으로 동시에 들어온 같은 키도 하나만 성공하게 한다.
- 같은 생성 요청의 모든 자녀 행은 하나의 트랜잭션에서 삽입한다.
- 부모가 `AVAILABLE` 퀘스트를 물리 삭제한 뒤 새 퀘스트를 만들 때는 이전 생성 요청 키를 재사용하지 않는다.
- 승인 시 부모 차감, 자녀 적립, 원장, 점수, 인증 승인, 퀘스트 완료를 한 트랜잭션으로 묶는다.
- 현금 보상이 있으면 기존 내부 송금 테이블과 지갑 잠금 순서를 재사용한다. 퀘스트 ID로부터 `QUEST_REWARD:{questId}` 형식의 내부 송금 식별 키를 만들고, 송금 실행이 퀘스트 승인 트랜잭션에 참여하도록 기존 송금 서비스에 내부 호출 경로를 추가한다.
- 현금 보상이 0원이면 송금 관련 처리를 호출하지 않는다.
- 성공 점수 이벤트 키는 `QUEST_COMPLETED:{questId}`, 최종 실패 점수 이벤트 키는 `QUEST_FAILED:{questId}`를 사용한다.
- 승인이나 실패 처리의 재요청은 퀘스트 상태, 내부 송금 식별 키와 점수 이벤트 키 검증으로 돈과 점수가 두 번 반영되지 않게 한다.

### 15.3 S3와 DB 경계

S3와 DB는 동일한 트랜잭션으로 묶을 수 없으므로 아래 순서로 처리한다.

```text
1차 상태 및 파일 검증
→ S3 업로드
→ DB 트랜잭션 시작
→ 퀘스트 잠금 및 재검증
→ 인증 이력 삽입
```

재검증 실패로 남은 S3 고아 객체는 90일 Lifecycle이 정리한다.

인증 제출에는 별도 요청 식별 키나 `submission_key`를 추가하지 않는다. S3 업로드 뒤 DB 트랜잭션에서 퀘스트를 잠그고 `IN_PROGRESS` 상태와 최신 인증을 다시 확인한다. 동시에 제출된 두 요청 중 하나만 인증 행을 만들고, 실패한 요청의 S3 객체는 사용자에게 노출하지 않은 채 Lifecycle에 맡긴다.

### 15.4 마감 처리

- 1분 주기의 서버 스케줄러가 `AVAILABLE → EXPIRED`, `IN_PROGRESS → FAILED`를 처리한다.
- `PENDING`은 마감 처리 대상에서 제외한다.
- 스케줄러 실행 전이라도 제출 요청 시 서버 시간으로 기한을 검증한다.
- 마감 시각과 제출 시각을 서버 시간의 초 단위로 비교하고, `submittedAt <= deadline`이면 제출 가능한 것으로 확정했다.
- 마감 대상은 `(status, deadline, id)` 인덱스로 최대 200건씩 조회하고, 각 200건을 별도 트랜잭션으로 처리한다.
- 여러 서버는 `FOR UPDATE SKIP LOCKED`로 이미 처리 중인 행을 기다리지 않고 건너뛴다.
- 한 번의 스케줄러 실행은 최대 2,000건 또는 20초 중 먼저 도달하는 시점에 끝낸다.
- 200건 묶음 트랜잭션 안에서 퀘스트마다 JDBC SAVEPOINT를 사용한다. Spring에서는
  `PROPAGATION_NESTED` 트랜잭션으로 구현한다.
- `IN_PROGRESS` 자동 실패는 퀘스트를 `FAILED`, `remaining_count = 0`으로 바꾸고, 티니점수
  대상이면 `QUEST_FAILED:{questId}` 이벤트로 `-2`를 적용한다. 상태와 점수는 같은 SAVEPOINT
  범위에서 함께 성공하거나 함께 롤백한다.
- 특정 퀘스트의 데이터·비즈니스 오류는 해당 SAVEPOINT까지만 롤백하고 같은 묶음의 정상
  퀘스트는 계속 처리한다. 실패한 퀘스트는 같은 스케줄러 실행에서 반복하지 않고 다음 1분
  주기에 다시 시도한다.
- DB 연결 장애처럼 트랜잭션을 계속 사용할 수 없는 시스템 오류는 200건 묶음 전체를
  롤백하고 다음 스케줄러 주기에 다시 시도한다.

## 16. 현재 범위에서 제외하거나 나중으로 미룬 기능

- 자동 시작 퀘스트
- 여러 자녀가 하나의 결과를 공유하는 협동 퀘스트
- 반복 또는 정기 퀘스트
- 소비 한도와 직접 연결되는 특수 퀘스트
- FCM/PWA 푸시 알림 실제 구현
- 자녀의 수동 확인 요청 버튼
- 거절 사유 통계 및 소비 리포트 시각화
- 부모가 티니점수 값을 직접 입력하는 기능
- 인증 방식 `BOTH_REQUIRED`
- 범용 퀘스트 워크플로 엔진
- 자녀가 부모 확인 전 `PENDING` 인증을 스스로 취소하는 기능

협동 퀘스트는 필요해질 때 현재 퀘스트를 억지로 확장하지 않고 별도 팀 퀘스트 모델로 설계한다.

### 16.1 자녀의 인증 제출 취소를 넣지 않는 이유 — 2026-08-11 결정, 팀 확인 필요

잘못된 사진이나 글을 제출했을 때 현재 설계의 복구 경로는 **부모 반려 → 재제출**이고,
3회 중 1회를 소모한다. 자녀가 스스로 취소하는 기능은 이 소모를 없애지만 비용이 크다.

- 인증 이력은 삭제하거나 덮어쓸 수 없다(불변식 8, §G). 취소된 시도도 행으로 남아야 하므로
  `T_QST_VERIFY_L.status`에 `CANCELED`를 추가해야 하고, CHECK 제약 변경이라 마이그레이션이 붙는다.
- `selectLatestVerification`이 취소된 행을 반환하게 되므로, 상세 조회·부모 검토 화면·남은
  기회 계산이 모두 "최신이 취소인 경우"를 처리해야 한다.
- `(quest_id, attempt_no)` 유일 제약 때문에 번호는 어차피 소모된다. 목적을 절반만 달성한다.
- `PENDING → IN_PROGRESS`를 자녀가 일으키는 전이는 §6.1에 없다. 확정된 상태 모델을 넓히는 변경이다.
- 부모가 검토 화면을 열어둔 상태에서 자녀가 취소하는 경쟁 경로가 새로 생긴다.

대신 **프런트엔드에서 제출 직전 미리보기와 확인 단계**로 대응한다. "되돌릴 수 없습니다"
같은 경고 문구가 아니라, 보낼 사진을 크게 보여주고 `이 사진으로 인증하기` / `다시 찍기`를
제시한다. 실수의 원인이 "확인하지 않고 눌렀다"이므로 보여주는 것이 정확한 대응이다.

이 항목은 원래 문서 어디에도 없었다. **미결이 아니라 누락이었고**, 다음 회의에서 확인받은 뒤
이 절의 제목에서 `팀 확인 필요`를 지운다.

## 17. 구현 전 반드시 기억할 현재 코드 상태

- 백엔드 경로: `TeenyMoney-Backend`
- 프론트엔드 경로: `TeenyMoney-FrontEnd/frontend`
- 백엔드는 Java 17, Spring MVC non-Boot, MyBatis, Tomcat 9, WAR 배포 구조다.
- 백엔드 도메인은 보통 `controller`, `dto/request`, `dto/response`, `service`, `mapper`, `vo`로 나뉜다.
- API 응답은 `ApiResponse<T>`, 예상 오류는 `BusinessException`과 도메인 `ErrorCode`를 사용한다.
- 컨트롤러와 DTO를 추가할 때 Swagger annotation도 함께 작성해야 한다.
- 프론트엔드는 Vue 기반이며 현재 퀘스트 페이지나 퀘스트 API 연동 코드가 없다.
- 백엔드에도 아직 퀘스트 controller/service/mapper/DTO/VO가 없다.

### 17.1 현재 퀘스트 DB

기준 스키마는 `sql/schema/teenymoney_schema_renamed.sql`이다.

현재 `T_QST_BASE_M` 필드:

```text
id, parent_id, child_id, title, content, deadline,
is_teeny_score, reward_amount, reward_teeny_score,
status, remaining_count, created_at, updated_at, completed_at
```

현재 허용 상태는 `AVAILABLE`, `IN_PROGRESS`, `PENDING`, `COMPLETED`, `FAILED`뿐이다. 목표 설계에 필요한 `EXPIRED`, `DECLINED`와 인증 방식, 거절 사유는 아직 없다.

현재 `T_QST_VERIFY_L` 필드:

```text
id, quest_id, image_url, content, status,
rejection_reason, created_at, updated_at, reviewed_at
```

`quest_id`에는 일반 인덱스만 있고 유일 제약은 없다. 따라서 현재 구조도 한 퀘스트에 여러 인증 행을 둘 수 있지만, 시도 순서를 명시하는 `attempt_no`와 이미지 키 컬럼은 아직 없다. FK는 퀘스트 삭제 시 인증을 함께 지우는 `ON DELETE CASCADE`다.

### 17.2 재사용할 기존 기능

- `global/storage/S3Storage`
  - 비공개 버킷 업로드 지원
  - 업로드 결과로 객체 키 반환
  - 객체 키를 presigned URL로 변환
  - 현재 삭제 기능은 없음
- `domain/wallet/service/WalletLedgerService`
  - 승인 시 부모 차감, 자녀 적립, 원장 기록에 활용
- `domain/wallet/service/TransferService`, `TransferExecutor`
  - 현재 일반 송금은 송금 실행 트랜잭션이 끝난 뒤 실패 상태를 별도로 기록하도록 분리되어 있다.
  - 그대로 호출하면 퀘스트 상태·점수와 송금을 하나의 트랜잭션으로 묶을 수 없으므로, 퀘스트 승인용 내부 호출은 기존 지갑 잠금과 원장 로직을 재사용하면서 바깥의 퀘스트 승인 트랜잭션에 참여하도록 보완해야 한다.
  - 현금 보상이 0원이면 송금 서비스를 호출하지 않는다.
- `domain/teenyscore/service/TeenyScoreChangeService`
  - 점수 0~1000 보정
  - 이벤트 키 중복 방지
  - 점수 이력과 현재 점수 변경을 트랜잭션으로 처리
- `domain/teenyscore/service/TeenyScorePolicyService`
  - 기존 금융 행동을 이벤트와 점수로 변환
  - 여기에 퀘스트 정책 생성 메서드를 추가하는 방향
- 가족 연결 및 접근 검증 기능
  - 부모와 자녀가 실제로 연결되어 있는지 검증할 때 재사용

현재 `TeenyScoreEventCode`에는 결제, 예금, 적금, 대출 이벤트만 있고 퀘스트 이벤트는 없다.

### 21.2 공통 조회 API와 커서 — 확정

- 부모·자녀 목록 API를 역할별로 분리하지 않고 `GET /quests?tab=AVAILABLE|ONGOING|COMPLETED` 하나로 제공한다.
- 상세 API는 `GET /quests/{questId}`를 사용한다.
- 부모와 자녀는 공통 응답 계약을 사용한다.
- 부모는 자신의 `parent_id`, 자녀는 자신의 `child_id`가 포함된 조회 조건으로 범위를 제한한다.
- 부모만 `childId` 필터를 사용할 수 있다. 자녀가 전달하면 무시하지 않고 `400`으로 응답한다.
- 조회 전용 서비스로 `QuestQueryService`를 추가한다.
- 첫 버전에는 `availableActions`, 부모 강조 카드 전용 요약 API, 역할별 정렬 규칙을 추가하지 않는다.
- `AVAILABLE` 탭은 `AVAILABLE`, `ONGOING` 탭은 `IN_PROGRESS`와 `PENDING`, `COMPLETED` 탭은 네 종료 상태를 조회한다.
- `AVAILABLE`과 `ONGOING`은 `(deadline ASC, questId ASC)` 커서를 사용한다.
- `COMPLETED`는 `(endedAt DESC, questId DESC)` 커서를 사용한다.
- 커서는 내부 필드를 노출하지 않는 문자열 `nextCursor`로 반환하며 탭이나 필터가 바뀌면 프론트가 버린다.

### 21.3 상태 변경, 인증 검토와 반려 — 확정

- 모든 상태 변경은 퀘스트 행을 잠근 뒤 권한, 현재 상태, 기한, 최신 인증을 다시 확인한다.
- 기한이 지난 `AVAILABLE`의 수정·삭제·수락·거절과 기한이 지난 `IN_PROGRESS`의 인증 제출은 `409`로 거절한다. 기한과 서버 시간이 정확히 같은 초이면 허용하며, `PENDING` 검토는 기한 경과로 막지 않는다.
- 전달한 인증 ID가 존재하지 않거나 해당 퀘스트의 인증이 아니면 `404`를 반환한다.
- 인증이 이미 처리됐거나 더 최신 인증이 있으면 `409`를 반환하고 프론트는 상세를 새로고침한다.
- 늦은 반려 요청은 아래 형태를 사용한다.

```text
{ reason, afterDeadlineAction?: EXTEND|FAIL, extendedDeadline? }
```

- 기한 전 첫 번째·두 번째 반려에는 `afterDeadlineAction`과 `extendedDeadline`을 사용하지 않는다.
- 기한 후 첫 번째·두 번째 반려에는 `afterDeadlineAction`이 필수다.
- `EXTEND`이면 미래의 `extendedDeadline`이 필수이고 퀘스트를 `IN_PROGRESS`로 돌린다.
- `FAIL`이면 연장 기한을 받지 않고 최종 `FAILED`로 처리한다.
- 세 번째 반려는 선택지 없이 항상 `FAILED`이며 남은 인증 기회는 0이다.

### 21.4 생성 요청의 중복 방지 — 확정

- 요청 식별 키는 반드시 필요한 API에만 사용한다.
- 퀘스트 일괄 생성 `POST /quests`에만 요청 식별 키를 필수로 사용한다.
- API는 `X-Creation-Request-Key` 헤더로 UUID를 받는다. 한 번의 사용자 생성 작업과 그 네트워크 재요청만 같은 값을 사용한다.
- 인증 제출과 나머지 상태 변경 API에는 요청 식별 키를 추가하지 않고 행 잠금, 상태, 최신 인증 검증으로 중복 처리를 막는다.
- 별도 생성 요청 테이블을 만들지 않고 자녀별 퀘스트 행에 `creation_request_key`를 저장한다.
- 같은 일괄 생성 요청으로 만들어진 자녀별 행은 같은 키를 가진다.
- `(parent_id, creation_request_key, child_id)` 유일 제약을 둔다.
- 생성 트랜잭션은 부모 회원 행을 먼저 잠가 같은 부모의 동일 키 요청을 순서대로 처리하고, 기존 키의 전체 자녀 집합과 내용을 비교한다.
- 같은 키와 같은 정규화된 내용·자녀 집합의 재요청은 기존 생성 결과를 반환한다.
- 같은 키를 다른 내용이나 다른 자녀 집합에 사용하면 `409`를 반환한다.
- 부모가 `AVAILABLE` 퀘스트를 물리 삭제한 뒤 새 생성 작업을 할 때는 이전 요청 키를 재사용하지 않는다.

### 21.5 인증 이미지와 S3 — 확정

- 인증 제출 순서는 기본 요청·파일 검증, 1차 상태 확인, S3 업로드, DB 트랜잭션, 퀘스트 잠금 및 재검증, 인증 이력 삽입 순이다.
- DB 저장이나 재검증 실패로 참조되지 않는 S3 객체가 생기면 사용자에게는 보이지 않으며 S3 Lifecycle이 업로드 90일 뒤 삭제한다.
- 정상 인증 이미지도 업로드 90일 뒤 삭제하고 텍스트, 상태, 시각, 반려 사유는 유지한다.
- 첫 버전에는 인증 이미지 직접 삭제 API를 만들지 않는다.
- 기존 `ImageFile` 검증을 그대로 재사용한다.
- 인증 시도당 사진은 최대 1장이며 크기는 최대 5MB다.
- 허용 형식은 `jpg`, `jpeg`, `png`, `webp`이고 파일 내용까지 검사한다.
- `HEIC`, GIF, 동영상은 첫 버전에서 제외한다.
- 인증 방식은 `FREE`, `PHOTO_REQUIRED`, `TEXT_REQUIRED`, `ANY_REQUIRED` 네 가지다.
- `FREE`에서 사진과 글이 모두 비어 있으면 프론트 확인창을 거친 뒤 제출할 수 있다.
- 공백만 입력한 인증 글은 빈 값으로 본다.
- S3 Lifecycle은 애플리케이션이 시작할 때 만들거나 변경하지 않고, 현재 프로젝트에서 백엔드와 AWS 버킷을 관리하는 사용자가 AWS를 사용하는 각 환경에 직접 적용한다.
- Lifecycle 규칙 이름은 `expire-quest-verifications-after-90-days`, 대상 prefix는 `quest-verifications/`, 상태는 `Enabled`, 현재 객체 만료 기간은 업로드 후 90일로 한다.
- 같은 버킷의 `profile/` 등 다른 prefix에는 이 규칙을 적용하지 않는다.
- 백엔드는 서버 시간을 기준으로 이미지 보관 기간이 끝나면 임시 조회 주소를 발급하지 않고 `imageExpired=true`를 반환한다. S3의 실제 삭제가 비동기로 늦어져도 사용자는 이미지를 볼 수 없다.
- 적용 담당자는 규칙의 활성 상태, prefix, 90일 만료 설정과 버킷 버전 관리 상태를 확인한다. 버전 관리가 켜져 있거나 중지된 버킷이면 삭제 표지만 남기고 객체 버전이 보존되지 않도록 이전 버전 삭제 규칙도 함께 확인한다.
- 테스트 퀘스트 객체에는 만료 예정 정보가 있고 프로필 객체에는 없는지 확인한다.
- 애플리케이션 실행 권한에는 S3 Lifecycle 설정 변경 권한을 부여하지 않는다.
- 참고: [AWS S3 Lifecycle prefix 필터](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html), [AWS 객체 만료 처리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html)

### 21.6 마감 처리 — 확정

- 초기 목표 규모는 전체 퀘스트 10만 건 이하로 잡는다.
- 퀘스트 생성, 수정, 인증 제출, 반려 연장, 자동 마감의 모든 기한 판단은 클라이언트 시간이 아닌 서버 시간을 기준으로 한다.
- 마감 시각과 서버가 기록한 제출 시각은 초 단위로 맞춰 비교하며 밀리초 이하는 사용하지 않는다.
- `submittedAt <= deadline`이면 제출을 허용하므로 정확히 같은 초에 제출한 요청도 유효하다.
- 화면 접속이나 새로고침은 상태나 점수를 변경하지 않고 최신 결과를 다시 조회하는 역할만 한다.
- 1분마다 서버 작업이 마감 대상을 처리한다.
- 전체 퀘스트를 조회하지 않고 `(status, deadline, id)` 인덱스를 사용한다.
- 조회 대상 상태를 `AVAILABLE`, `IN_PROGRESS`로 명시한다. `PENDING`과 모든 종료 상태는 조회하지 않는다.
- `AVAILABLE`의 기한이 지나면 `EXPIRED`, `IN_PROGRESS`의 기한이 지나면 `FAILED`로 바꾼다.
- 한 번의 조회는 최대 200건이다.
- 200건 단위마다 별도 트랜잭션으로 처리하고 커밋하여 잠금을 오래 유지하지 않는다.
- 묶음 안에서는 퀘스트마다 `PROPAGATION_NESTED`를 사용해 JDBC SAVEPOINT를 만든다. 한
  퀘스트의 상태·점수 처리가 실패해도 그 퀘스트만 롤백하고 같은 묶음의 성공 건은 커밋한다.
- 실패한 퀘스트는 같은 실행에서 반복 처리하지 않고 다음 1분 주기에 재시도한다. 시스템
  오류는 묶음 전체를 롤백한다.
- 한 차례 실행은 최대 2,000건 또는 20초 중 먼저 도달하는 시점까지 처리하고 나머지는 다음 실행에서 이어서 처리한다.
- 여러 서버가 실행하더라도 같은 퀘스트를 동시에 처리하지 않도록 DB 행 잠금을 사용한다.
- 대상 조회에는 `FOR UPDATE SKIP LOCKED`를 사용해 다른 서버가 이미 잠근 행은 기다리지 않고 건너뛴다.

### 21.7 권한과 오류 노출 — 확정

- 로그인하지 않은 요청은 `401`, 역할에 맞지 않는 기능 호출은 구체적인 메시지를 포함한 `403`을 반환한다.
- 연결되지 않은 자녀를 직접 지정한 요청은 `403`을 반환한다.
- 퀘스트 ID 조회는 로그인 사용자의 부모 ID 또는 자녀 ID 범위를 조회 조건에 포함한다.
- 다른 가족의 퀘스트와 실제로 없는 퀘스트는 모두 `404 QUEST_NOT_FOUND_OR_ACCESS_DENIED`로 응답해 존재 여부를 노출하지 않는다.
- 사용자에게 안전한 상황은 구체적인 오류 코드와 메시지를 제공한다.
- 서버 기록에는 실제 실패 원인을 남기되 사용자 응답에는 SQL, 내부 경로, 다른 가족의 식별 정보를 포함하지 않는다.

퀘스트 전용 오류는 다음과 같이 사용한다.

| HTTP | 코드 | 사용자 메시지 |
|---:|---|---|
| 400 | `QUEST_CHILD_REQUIRED` | 퀘스트를 받을 자녀를 한 명 이상 선택해 주세요. |
| 400 | `QUEST_CHILD_DUPLICATED` | 같은 자녀를 중복해서 선택할 수 없습니다. |
| 400 | `QUEST_REWARD_INVALID` | 현금 보상은 0원 또는 100원 이상이어야 하며, 현금이나 티니점수 중 하나는 필요합니다. |
| 400 | `QUEST_DEADLINE_INVALID` | 기한은 현재보다 미래이며 1년 이내여야 합니다. |
| 400 | `QUEST_VERIFICATION_REQUIREMENT_UNMET` | 이 퀘스트의 인증 방식에 필요한 사진 또는 글이 없습니다. |
| 400 | `QUEST_REVIEW_REQUEST_INVALID` | 반려 요청의 사유와 기한 후 처리 방법을 확인해 주세요. |
| 400 | `QUEST_EXTENDED_DEADLINE_INVALID` | 연장 기한은 현재보다 미래이며 1년 이내여야 합니다. |
| 400 | `QUEST_CREATION_KEY_INVALID` | 요청 식별 키를 확인해 주세요. |
| 403 | `QUEST_PARENT_ONLY` | 부모만 사용할 수 있는 기능입니다. |
| 403 | `QUEST_CHILD_ONLY` | 자녀만 사용할 수 있는 기능입니다. |
| 403 | `QUEST_CHILD_NOT_LINKED` | 연결된 자녀의 퀘스트만 처리할 수 있습니다. |
| 404 | `QUEST_NOT_FOUND_OR_ACCESS_DENIED` | 퀘스트를 찾을 수 없거나 접근할 수 없습니다. |
| 409 | `QUEST_STATUS_CONFLICT` | 현재 퀘스트 상태에서는 처리할 수 없습니다. 새로고침해 주세요. |
| 409 | `QUEST_DEADLINE_PASSED` | 퀘스트 기한이 지났습니다. 새로고침해 주세요. |
| 409 | `QUEST_VERIFICATION_CONFLICT` | 최신 대기 중 인증만 처리할 수 있습니다. 새로고침해 주세요. |

- 부모 잔액 부족은 기존 `INSUFFICIENT_BALANCE`를 재사용하고 프론트는 `지갑 충전하기`를 표시한다.
- 이미지 검증과 업로드 오류는 기존 `STORAGE_*` 오류를 재사용한다.
- 로그인 필요는 기존 `AUTH_UNAUTHORIZED`를 재사용한다.
- 제목, 본문, 거절 사유처럼 특정 입력 필드의 문제는 `COMMON_INVALID_INPUT`의 `data`에 필드별 메시지를 담는다.
- 프론트는 일반적인 `400`에서 입력 내용을 수정하고, `409`에서 목록 또는 상세를 새로고침한다.

### 21.8 생성, 보상, 입력 검증과 충전 흐름 — 확정

- 여러 자녀 생성은 선택한 모든 자녀의 행이 생성되거나 하나도 생성되지 않는 한 트랜잭션으로 처리한다.
- 같은 자녀 ID를 중복 전달하면 조용히 합치지 않고 `400`으로 응답한다.
- 현금 보상에는 서비스 상한을 두지 않는다.
- 단, DB `BIGINT`·Java `Long` 범위를 넘거나 대상 자녀 수를 곱한 총 예상 보상이 숫자 범위를 넘는 값은 잘못된 요청으로 거절한다.
- 현금 보상을 사용하면 최소 금액은 100원이며 원 단위 정수만 허용한다.
- 현금 보상을 사용하지 않으면 0원이고, 현금 0원이면서 티니점수도 적용하지 않는 퀘스트는 만들 수 없다.
- 생성 전 프론트 확인창에 대상 자녀 수, 1인당 보상, 총 예상 보상, 현재 부모 지갑 잔액을 표시한다.
- 생성 시 돈을 미리 차감하거나 확보하지 않는다.
- 승인 시 부모 잔액이 부족하면 퀘스트와 인증을 `PENDING`으로 유지한다.
- 현금 보상이 0원이면 지갑과 송금 처리를 건너뛰고 티니점수 및 상태 변경만 처리한다.
- 프론트는 `지갑 충전하기` 버튼으로 충전 화면에 이동시키고, 충전 완료 후 부모가 다시 승인한다.
- 승인과 카드 결제를 하나의 서버 작업으로 묶지 않는다.
- 제목은 앞뒤 공백 제거 후 1~50자, 본문은 앞뒤 공백 제거 후 1~500자다.
- 공백만 입력한 제목이나 본문은 허용하지 않는다.
- 인증 글은 앞뒤 공백 제거 후 최대 500자다. 인증 방식에 따라 선택 사항일 수 있지만 입력했다면 공백만 남을 수 없다.
- 자녀 거절 상세 설명은 앞뒤 공백 제거 후 최대 500자다. `OTHER`를 선택한 경우 1자 이상 필수다.
- 부모 반려 사유는 선택 사항이다. 값이 없거나 공백뿐이면 `NULL`로 저장하고, 값이 있으면 앞뒤 공백 제거 후 1~500자여야 한다.
- 최초 기한은 생성 시점보다 미래이며 생성 시점부터 최대 1년 이내다.
- 연장 기한은 반려 처리 시점보다 미래이며 반려 처리 시점부터 최대 1년 이내다.
- 인증 기회가 3회로 제한되어 있으므로 별도 연장 횟수 제한은 추가하지 않는다.

### 21.9 목록과 상세 응답 — 확정

- 목록은 기본 20건이며 `items`, `nextCursor`를 반환한다. 별도 `hasNext`는 두지 않는다.
- 목록 항목은 `questId`, 자녀 ID·이름·프로필 이미지, `title`, `deadline`, `rewardAmount`, `teenyScoreEnabled`, `verificationRequirement`, `status`, `remainingCount`, `endedAt`을 포함한다.
- 상세는 목록 필드에 본문, 생성 시각, 종료 시각, 자녀 거절 사유·상세 설명, 최신 인증 1건을 추가한다.
- 최신 인증은 인증 ID, 시도 번호, 인증 글, 이미지 임시 주소, 이미지 보관 기간 만료 여부, 인증 상태, 반려 사유, 제출 시각, 검토 시각을 포함한다.
- 첫 버전에는 과거 인증 전체 목록, 서버가 계산한 버튼 목록, S3 객체 키, 부모 전용 집계, 목록 본문과 목록 인증 이미지를 반환하지 않는다.

### 21.10 테스트 전략과 완료 기준 — 확정

첫 버전은 모든 API 조합을 기계적으로 반복하지 않고, 오류가 발생했을 때 금전·점수·상태가 어긋날 위험이 큰 부분을 중심으로 세 단계로 검사한다. 현재 프로젝트가 사용 중인 JUnit 5, Mockito, MockMvc와 선택적인 실제 DB 통합 테스트 방식을 그대로 사용하며 새 테스트 도구를 추가하지 않는다.

1. 서비스 테스트
   - 생성·수정·삭제와 모든 허용 상태 전이를 검사한다.
   - 허용되지 않은 상태 전이, 부모·자녀 역할 위반, 연결되지 않은 자녀 접근을 차단하는지 검사한다.
   - 인증 제출, 최신 `PENDING` 인증 검토, 반려 후 남은 기회 감소, 세 번째 반려의 `FAILED` 처리를 검사한다.
   - 승인 성공 시 보상 송금·점수 반영·인증 승인·퀘스트 완료가 함께 처리되는지 검사한다.
   - 잔액 부족이나 처리 실패 시 인증과 퀘스트가 `PENDING`으로 유지되고 돈과 점수가 일부만 반영되지 않는지 검사한다.
2. API 계약 테스트
   - 요청값 검증, 역할별 허용 API, HTTP 상태와 퀘스트 오류 코드, 공통 오류 응답의 `data`를 검사한다.
   - 목록과 상세 응답이 확정된 필드만 제공하고 내부 S3 객체 키와 다른 가족 정보를 노출하지 않는지 검사한다.
3. DB·트랜잭션 통합 테스트
   - 역할별 조회 범위, 탭별 정렬, 커서 다음 페이지, 최신 인증 조회를 실제 SQL로 검사한다.
   - 생성 요청 식별 키의 고유 제약과 여러 자녀 생성의 전체 성공 또는 전체 취소를 검사한다.
   - 승인 동시 요청, 인증 동시 제출, 명령 처리와 마감 처리의 경합에서도 보상·점수·상태 변경이 한 번만 반영되는지 검사한다.
   - 마감 조회가 `(status, deadline, id)` 인덱스를 사용하고 한 번에 최대 200건만 잠그는지 검사한다.

S3는 테스트마다 실제 업로드하지 않는다. 서비스 테스트에서는 저장 기능을 대신하는 객체를 사용하고, 이미지 확장자·크기·실제 형식 검증은 기존 `ImageFile` 테스트에 퀘스트 조건을 추가한다. 운영 S3의 90일 삭제 정책은 애플리케이션 테스트와 분리해 확인한다.

대표 전체 흐름은 다음만 유지한다.

- 현금과 티니점수가 있는 퀘스트의 생성 → 수락 → 인증 → 승인 → 완료
- 부모 잔액 부족 → `PENDING` 유지 → 충전 후 재승인
- `AVAILABLE` 만료의 `EXPIRED` 처리와 `IN_PROGRESS` 만료의 `FAILED` 처리
- 기한 후 반려 연장과 세 번째 반려의 최종 `FAILED` 처리
- 여러 자녀 생성의 전체 성공과 한 자녀 검증 실패 시 전체 취소

퀘스트 기능의 완료 조건은 다음과 같다.

- 위 테스트가 모두 통과한다.
- 기존 전체 테스트가 깨지지 않는다.
- Java 컴파일과 WAR 빌드가 성공한다.
- 새 DB에서 마이그레이션과 시드가 순서대로 적용된다.
- 구현된 API 경로, 요청·응답 필드와 오류 코드가 이 문서 및 Swagger 명세와 일치한다.
- 10만 건 이하 초기 목표에서 마감 배치가 200건 단위, 실행당 최대 2,000건 또는 20초 제한을 지킨다.

### 21.11 퀘스트 설계 이후의 다음 단계

- 월간 등급 저장 구조와 월 경계 처리 방식은 티니점수·금융 도메인의 별도 후속 설계로 넘긴다. 퀘스트 코드 작업은 먼저 할 수 있지만 티니점수 대상 퀘스트의 운영 공개 전에는 반드시 완료한다.
- 퀘스트 전체 설계는 사용자 최종 승인을 받았으며 `#102`부터 순서대로 구현한다.

## 23. #102 구현 기록

### 23.1 구현 범위

- DB 확장 스크립트는 기존 마지막 번호 `V011` 다음인 `V012__extend_quest_domain.sql`로 작성한다.
- `T_QST_BASE_M`에 생성 요청 식별 키, 인증 방식, 자녀 거절 사유와 종료 시각을 반영하고 상태를 7개로 확장한다.
- 수락 여부는 `IN_PROGRESS` 상태로 충분하고 화면이나 업무 규칙에서 정확한 수락 시각을 사용하지 않으므로 `accepted_at`은 저장하지 않는다.
- `T_QST_VERIFY_L`은 S3 URL 대신 객체 키를 저장하고 퀘스트별 시도 번호를 가진다.
- 부모 생성은 자녀마다 독립된 퀘스트 행을 한 작업 안에서 만들며 생성된 ID를 요청 자녀 순서대로 반환한다.
- 생성 요청 식별 키는 `POST /quests`에서만 `X-Creation-Request-Key` UUID 헤더로 받는다. 같은 키와 같은 내용의 다시 보내기는 기존 ID를 반환하고, 다른 내용이면 `409`로 응답한다.
- 부모 수정과 실제 삭제는 부모 소유 행을 잠근 뒤 `AVAILABLE` 상태와 서버 기준 마감 시각을 다시 확인한다.
- 서버 시각과 마감 시각이 정확히 같은 초라면 수정과 삭제를 허용한다. 서버 시각이 마감 시각을 지난 초부터 `409 QUEST_DEADLINE_PASSED`다.
- 수정 또는 삭제 직전에 상태가 바뀌어 실제 처리 행이 0건이면 `409 QUEST_STATUS_CONFLICT`다.

### 23.2 조회와 HTTP 계약

- 부모와 자녀 모두 공통 `GET /api/v1/quests`와 `GET /api/v1/quests/{questId}`를 사용한다.
- 부모 목록 SQL은 로그인한 `parent_id`를, 자녀 목록 SQL은 로그인한 `child_id`를 조회 조건에 직접 포함한다.
- 부모는 `childId`로 자신의 퀘스트를 좁힐 수 있고 자녀가 `childId`를 보내면 `400 COMMON_INVALID_INPUT`이다.
- `AVAILABLE`, `ONGOING`은 `(deadline ASC, questId ASC)`, `COMPLETED`는 `(endedAt DESC, questId DESC)` 순서다.
- 목록 SQL은 최대 21건을 읽고 응답에는 20건만 담는다. 21번째 행이 있을 때만 20번째 행 기준 `nextCursor`를 반환한다.
- 커서는 요청 탭을 포함하며 다른 탭에서 재사용하거나 해석할 수 없는 값이면 `400 COMMON_INVALID_INPUT`이다.
- 상세 조회는 역할별 접근 조건을 SQL에 포함한다. 존재하지 않는 퀘스트와 다른 가족의 퀘스트는 모두 `404 QUEST_NOT_FOUND_OR_ACCESS_DENIED`다.
- 자녀 프로필과 아직 보관 기간이 남은 최신 인증 이미지만 S3 임시 조회 주소로 변환한다. 인증 이미지가 업로드 후 정확히 90일이 되면 `imageUrl=null`, `imageExpired=true`다.
- `POST /api/v1/quests`는 생성된 퀘스트 ID 목록, `PATCH /api/v1/quests/{questId}`는 저장 후 새 상세, `DELETE /api/v1/quests/{questId}`는 성공 응답의 `data=null`을 반환한다.
- 생성·수정·삭제 컨트롤러에는 부모 역할 검사를 적용하고 서비스에서도 역할을 다시 확인한다.

### 23.3 현재 검증 상태

- 역할별 목록·상세, 20건 커서, 잘못된 커서, 최신 인증, 이미지 90일 경계 서비스 테스트를 작성했다.

- MyBatis 컨텍스트에서 모든 퀘스트 SQL 등록과 부모·자녀 범위 조건, 탭별 정렬을 확인했다.

## 28. 위치 기반 퀘스트 확장 검토 — 일부 확정

- 웹의 위치 권한을 사용해 자녀가 인증 제출 시점의 현재 위치를 한 번 전달하는 방식으로 구현한다. 지속적인 이동 경로 추적은 하지 않는다.
- 위치는 사진이나 글에 항상 추가되는 조건이 아니라 독립적인 인증 수단이다. 위치 인증만으로도 인증 제출이 가능해야 한다.
- 부모는 지도에서 주소를 검색하고 핀을 옮겨 목표 지점을 지정한다.
- 위치와 사진을 함께 요구하는 방식도 지원한다. 사진 파일의 EXIF 위치는 신뢰하지 않고, 촬영·제출 시점에 브라우저가 제공한 좌표와 사진을 같은 인증 이력으로 서버에 전달해 각각 검증한다.
- 사진·위치 인증은 갤러리 파일 선택을 제공하지 않고 앱 화면에서 새 사진 촬영만 허용한다. 웹 서버는 이미지 바이트만으로 실제 촬영 시점을 완벽히 증명할 수 없으므로, 공식 FE에서 `getUserMedia()` 촬영 흐름만 제공하는 수준을 보장 범위로 둔다.
- FE는 먼저 현재 위치와 정확도를 확인해 허용 범위일 때만 카메라를 열고, 촬영 직후 위치를 다시 확인한다. 최종 제출에서는 서버가 목표 좌표와 제출 좌표의 거리를 다시 계산하며 범위 밖이면 인증 이력을 만들거나 이미지를 저장하지 않는다.
- 위치 인증의 허용 반경은 모든 퀘스트에 공통으로 `100m`를 적용한다. 서버가 계산한 거리가 목표 좌표로부터 `100m 이하`이면 범위 안으로 인정하고, `100m 초과`이면 거절한다. 부모가 퀘스트별로 반경을 변경하는 기능은 두지 않는다.
- 목표 좌표와 허용 범위 판정은 프론트엔드 결과를 신뢰하지 않고 서버에서 다시 계산한다.
- 위치 권한 거절, 위치 서비스 비활성화, 낮은 위치 정확도와 좌표 위조 가능성을 고려한다.
- GPS 정확도 기준, 좌표 보관 기간과 기존 인증 방식 모델에 반영하는 방법은 아직 확정하지 않았다.
