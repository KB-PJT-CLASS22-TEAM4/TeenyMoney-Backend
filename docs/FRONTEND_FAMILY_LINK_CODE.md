# 가족 연동 코드 API 연동 안내

부모가 6자리 코드를 발급받고, 자녀가 그 코드를 입력해 가족에 연동하는 기능입니다.
이 문서는 **프론트엔드가 반드시 지켜야 하는 규칙**을 담고 있습니다. 지키지 않으면
사용자에게 이미 무효가 된 코드가 화면에 표시되는 문제가 생깁니다.

계약의 기준은 Swagger입니다. 이 문서는 Swagger가 표현하지 못하는 **동작 규칙**을 보충합니다.
일반 연동 규칙은 [FRONTEND_DEV.md](FRONTEND_DEV.md)를 함께 보십시오.

---

## 1. 엔드포인트

```text
POST /api/v1/families/make-codes
```

| 항목 | 값 |
|---|---|
| 인증 | 필수. `Authorization: Bearer <accessToken>` |
| 권한 | **PARENT 회원만.** CHILD 토큰은 403 |
| 요청 본문 | 없음 |
| 필수 헤더 | `Idempotency-Key` (아래 3장 참고) |

### 요청

```http
POST /api/v1/families/make-codes
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 8f14e45f-ceea-4d4b-9a2f-1c3d5e7a9b11
```

### 성공 응답 (200)

```json
{
  "success": true,
  "code": "OK",
  "message": "성공",
  "data": {
    "code": "048291",
    "expiresAt": "2026-08-06T14:35:12.482+09:00"
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `data.code` | string | 6자리 숫자 문자열. **숫자로 파싱하지 마십시오** — `048291`의 앞자리 0이 사라집니다 |
| `data.expiresAt` | string | ISO-8601 오프셋 시각. 남은 유효시간을 서버가 계산해 내려줍니다 |

## 2. 동작 규칙 — 화면 설계 전에 읽어야 합니다

### 2.1 부모 한 명에게 유효한 코드는 항상 하나입니다

새로 발급하면 **직전 코드는 그 즉시 무효**가 됩니다. 자녀가 이전 코드를 입력하면 실패합니다.

이 때문에 "코드 재발급" 버튼은 사실상 "이전 코드 취소 + 새 코드 발급"입니다.
사용자가 이미 자녀에게 코드를 불러준 상태라면 재발급이 그것을 무효화한다는 점을,
버튼 문구나 확인 문구로 알려주는 편이 좋습니다.

### 2.2 코드는 1회용입니다

자녀 한 명이 사용하면 즉시 소멸합니다. 둘째 자녀를 연동하려면 다시 발급받아야 합니다.

### 2.3 유효시간은 10분입니다

`expiresAt`을 그대로 쓰십시오. 클라이언트에서 "지금 + 10분"으로 직접 계산하면 안 됩니다.
재시도로 받은 응답은 발급 시각이 과거라 실제보다 늦은 시각이 나옵니다.

### 2.4 연속 발급은 5초 간격으로 제한됩니다

5초 안에 **다른** 의도로 다시 발급하면 429가 내려옵니다. 같은 의도의 재시도는
제한에 걸리지 않습니다(3장 참고).

## 3. Idempotency-Key — 가장 중요한 부분

### 3.1 왜 필요한가

발급 요청 하나가 네트워크 사정으로 늦어지고 그 사이 재시도가 나가면, 서버 입장에서는
두 요청이 똑같이 생겼습니다. **"재시도라 같은 코드를 원하는 것"인지 "새 코드를 원하는 것"인지
판단할 근거가 요청 안에 없습니다.**

키가 없으면 이렇게 됩니다.

```text
t=0   요청 A 발급 → 코드 111111 생성 (응답 지연 중)
t=6   재시도 B 발급 → 111111 무효화, 222222 생성
t=7   B 응답 도착 → 화면에 222222
t=8   A 응답 뒤늦게 도착 → 화면에 111111   ← 이미 죽은 코드
```

사용자는 111111을 자녀에게 불러주고, 자녀는 "유효하지 않은 코드"를 봅니다.

### 3.2 규칙

> **키는 사용자가 버튼을 누르는 순간 만들고, 그 누름에 대한 모든 재전송에 같은 키를 씁니다.**

여기서 "한 번의 누름"을 **발급 의도**라고 부릅니다. HTTP 요청 1건이 아니라
사용자가 "코드 줘"라고 마음먹은 한 번입니다.

| 상황 | 의도 | HTTP 요청 | 키 |
|---|---|---|---|
| 버튼 1번 누름 | 1개 | 1개 | 새 UUID |
| 누름 → 타임아웃 → 자동 재시도 | **1개** | 2개 | **같은 UUID** |
| 누름 → 응답 → 나중에 다시 누름 | **2개** | 2개 | 각각 다른 UUID |

### 3.3 구현

```javascript
async function issueLinkCode() {
  const intentKey = crypto.randomUUID();   // 버튼 핸들러 진입 시 1회

  return withRetry(3, () =>
    fetch('/api/v1/families/make-codes', {
      method: 'POST',
      headers: {
        'Authorization': `Bearer ${accessToken}`,
        'Idempotency-Key': intentKey,      // 재시도 전부 같은 값
      },
    })
  );
}
```

사용자가 다시 누르면 `issueLinkCode()`가 다시 호출되어 `intentKey`가 새로 만들어집니다.
그래서 새 코드가 나오고 이전 코드가 무효가 됩니다. 의도한 동작입니다.

### 3.4 하면 안 되는 것

```javascript
// ✗ 재시도 루프 안에서 생성 - 시도마다 새 의도가 되어 아무 효과가 없다
withRetry(3, () =>
  fetch(url, { headers: { 'Idempotency-Key': crypto.randomUUID() } }));

// ✗ 화면 진입 시 1회 생성해 계속 재사용 - 사용자가 영영 새 코드를 못 받는다
const [key] = useState(() => crypto.randomUUID());

// ✗ 안정적인 값 사용 - memberId나 날짜는 '의도'가 아니다
headers: { 'Idempotency-Key': String(memberId) }
```

### 3.5 서버 동작

| 상황 | 헤더 | 결과 |
|---|---|---|
| 첫 발급 | `key-A` | 새 코드 `111111` |
| 타임아웃 재시도 | `key-A` | **`111111` 그대로.** 발급하지 않고 쿨다운도 소모하지 않음 |
| 사용자가 다시 누름 | `key-B` | 새 코드 `222222`, `111111` 즉시 무효 |
| 헤더 없음 | — | **400 `COMMON_MISSING_HEADER`** |
| 값이 비었거나 100자 초과 | `""` / 긴 값 | **400 `FAMILY_IDEMPOTENCY_KEY_INVALID`** |

키의 수명은 코드와 같은 10분입니다. 10분이 지난 뒤 같은 키로 오면 새 코드가 나갑니다.
그 시점에는 원래 코드도 만료됐으므로 재시도할 의미가 없습니다.

### 3.6 값 제약

| 항목 | 제약 |
|---|---|
| 필수 여부 | **필수.** 없으면 400 |
| 길이 | 1~100자. UUID는 36자 |
| 권장 형식 | `crypto.randomUUID()` 결과 |

> 서버가 키를 대신 만들어주지 않습니다. 만들어주면 요청마다 다른 의도가 되어
> 중복 제거가 성립하지 않는데, 그 사실이 겉으로 드러나지 않은 채 3.1의 문제가
> 그대로 남기 때문입니다. 없으면 조용히 넘어가는 대신 거절합니다.

## 4. 오류 응답

응답 껍데기는 다른 API와 같습니다. `success`로 분기하고 `message`를 그대로 노출하면 됩니다.

```json
{
  "success": false,
  "code": "FAMILY_LINK_CODE_TOO_SOON",
  "message": "잠시 후 다시 시도해 주세요.",
  "data": null
}
```

| HTTP | code | 의미 | 화면 처리 |
|---|---|---|---|
| 400 | `COMMON_MISSING_HEADER` | `Idempotency-Key` 없음 | **구현 실수입니다.** 3장을 다시 확인하십시오 |
| 400 | `FAMILY_IDEMPOTENCY_KEY_INVALID` | 키가 비었거나 100자 초과 | 위와 동일 |
| 401 | `AUTH_*` | 토큰 없음·만료 | 재발급 후 재시도, 실패 시 로그인 |
| 403 | `AUTH_FORBIDDEN` | PARENT 회원이 아님 | 자녀 계정에는 이 버튼을 노출하지 않습니다 |
| 429 | `FAMILY_LINK_CODE_TOO_SOON` | 5초 쿨다운 | `message` 노출. **자동 재시도 금지** |
| 503 | `COMMON_SERVICE_UNAVAILABLE` | 코드 공간 포화 | 잠시 후 재시도 안내 |
| 400 | `FAMILY_LINK_CODE_INVALID` | 만료·사용됨·잘못된 코드 | 자녀 연동 화면에서 사용 |

429는 **재시도하면 안 됩니다.** 같은 의도의 재시도는 애초에 429가 나지 않으므로,
429가 왔다는 것은 사용자가 너무 빨리 다시 눌렀다는 뜻입니다. 버튼을 잠시 비활성화하십시오.

## 5. 프론트엔드 체크리스트

- [ ] `Idempotency-Key` 헤더를 **반드시** 전송 (없으면 400)
- [ ] 버튼 핸들러 진입 시 `crypto.randomUUID()`로 키를 만들고, 재시도에 같은 키를 재사용
- [ ] `data.code`를 문자열로 다룸 (숫자 변환 금지 — 앞자리 0 손실)
- [ ] 남은 시간 표시에 `data.expiresAt` 사용 (클라이언트에서 10분 계산 금지)
- [ ] 요청 진행 중 버튼 비활성화 (불필요한 요청 감소)
- [ ] 429는 재시도하지 않고 안내만
- [ ] CHILD 계정에는 발급 버튼 미노출
- [ ] 재발급이 이전 코드를 무효화한다는 점을 사용자에게 안내
- [ ] 타임아웃 시 이전 요청을 `AbortController`로 취소 (권장)

## 6. 자녀 연동 API

**아직 구현되지 않았습니다.** 코드 소비 로직(`consumeCode`)은 서버에 준비되어 있으나
엔드포인트가 열려 있지 않습니다. 시도 횟수 제한과 함께 별도 이슈로 추가될 예정입니다.

그때까지 자녀 연동 화면은 개발을 시작하되 실제 호출은 대기하십시오.
경로와 요청 형식이 정해지면 이 문서에 추가됩니다.
