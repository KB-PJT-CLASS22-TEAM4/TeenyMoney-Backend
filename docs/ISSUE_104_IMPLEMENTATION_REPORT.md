## 1. 구현 결과

부모가 자녀의 최신 퀘스트 인증을 승인하거나 반려하는 이슈 #104 범위를 구현했다.

### 승인 API

```text
PATCH /quests/{questId}/verifications/{verificationId}/approve
```

- 부모 소유 퀘스트만 처리한다.
- 퀘스트와 최신 인증을 순서대로 잠근다.
- 퀘스트와 인증이 모두 `PENDING`이고 요청한 인증이 최신일 때만 승인한다.
- 현금 보상이 0원보다 크면 부모 MEMBER 지갑에서 자녀 MEMBER 지갑으로 즉시 송금한다.
- 송금 유형은 `QUEST_REWARD`, 멱등성 키는 `QUEST_REWARD:{questId}`다.
- 티니점수 대상이면 `QUEST_COMPLETED:{questId}` 이벤트로 `+3`을 적용한다.
- 인증은 `APPROVED`, 퀘스트는 `COMPLETED`가 된다.
- 처리 후 기존 `QuestDetailResponseDTO` 전체를 다시 조회해 반환한다.

승인의 송금 행 생성, 부모 차감, 자녀 적립, 원장 기록, 점수 변경, 인증 승인,
퀘스트 완료는 하나의 Spring 트랜잭션에 참여한다. 후속 단계 하나라도 실패하면 전체가
롤백된다.

### 반려 API

```text
PATCH /quests/{questId}/verifications/{verificationId}/reject
```

요청 본문은 다음 필드를 사용한다.

```json
{
  "reason": "인증 사진에서 완료 여부를 확인할 수 없어요.",
  "afterDeadlineAction": "EXTEND",
  "extendedDeadline": "2026-08-20T20:00:00"
}
```

반려 상태 전이는 다음과 같다.

| 조건 | 결과 | 남은 횟수 | 점수 |
|---|---|---:|---:|
| 기한 전, 재시도 가능 | `IN_PROGRESS` | 1 감소 | 0 |
| 기한 후 `EXTEND` | `IN_PROGRESS`, 기한 변경 | 1 감소 | 0 |
| 기한 후 `FAIL` | `FAILED` | 1 감소 | 대상이면 -2 |
| 마지막 기회 반려 | 항상 `FAILED` | 0 | 대상이면 -2 |

- 서버 시각과 기한이 같은 초는 아직 기한 전으로 판단한다.
- 연장 기한은 처리 시각보다 미래이고 최대 1년 이내다.
- 마지막 기회 반려에서는 전달된 기한 후 선택값을 무시하고 항상 실패한다.
- 최종 실패 이벤트 키는 `QUEST_FAILED:{questId}`라서 점수 감점은 한 번만 기록된다.
- 반려 사유는 선택 사항이다. 값이 없거나 공백뿐이면 `NULL`로 저장하고, 값이 있으면 앞뒤 공백 제거 후 1~500자다.

### 오류와 경합 처리

- 최신 인증 ID가 아니거나 이미 처리된 인증: `409 QUEST_VERIFICATION_CONFLICT`
- 퀘스트 상태 경합: `409 QUEST_STATUS_CONFLICT`
- 잘못된 반려 조합: `400 QUEST_REVIEW_REQUEST_INVALID`
- 잘못된 연장 기한: `400 QUEST_EXTENDED_DEADLINE_INVALID`
- 부모 잔액 부족: 기존 `INSUFFICIENT_BALANCE`
- 잔액 부족이면 퀘스트와 인증은 `PENDING`으로 유지되고 점수도 변하지 않는다.
- SQL 갱신에도 `status = 'PENDING'` 조건을 두고 갱신 건수가 1이 아니면 409를 반환한다.
- 송금 멱등성 키, 점수 이벤트 키, 퀘스트·인증 잠금, 조건부 UPDATE를 함께 사용한다.

## 3. 핵심 구현 방식

### 트랜잭션 경계

기존 `TransferService.executeTransfer`는 실패 행을 별도 트랜잭션에 기록하기 위해
`NOT_SUPPORTED`로 설계되어 있었다. 이를 승인 서비스에서 그대로 호출하면 퀘스트 승인과
송금이 분리된다. 기존 동작은 유지하고, 새 메서드
`transferInExistingTransaction`을 `Propagation.MANDATORY`로 추가했다.

따라서 일반 송금의 실패 기록 방식은 깨뜨리지 않으면서 퀘스트 보상만 반드시 호출자의
승인 트랜잭션 안에서 실행된다.

### 잠금 순서와 동시성

1. 부모 ID 조건으로 퀘스트 행 `FOR UPDATE`
2. 최신 인증 한 건을 `attempt_no DESC, id DESC LIMIT 1 FOR UPDATE`
3. 보상이 있으면 기존 송금 실행기가 송금 행과 두 지갑을 잠금
4. 점수 행 잠금 및 이벤트 키 중복 확인
5. 인증과 퀘스트를 `PENDING` 조건부 갱신

동시에 승인과 반려가 들어오면 퀘스트 잠금에서 직렬화되고, 먼저 커밋된 결과를 본 두 번째
요청은 409로 끝난다. DB 갱신 조건과 멱등성 키는 잠금 외의 마지막 방어선이다.

### 티니점수

부모는 점수 수치를 정하지 않는다. 퀘스트 생성 때 티니점수 대상 여부만 정하며 승인·반려
시점에는 바꿀 수 없다.

- 대상 성공: `+3`
- 대상 최종 실패: `-2`
- 단순 반려와 재시도: `0`
- 월간 점수 상한과 월간 점수 퀘스트 개수 제한: 없음

기존 `TeenyScoreChangeService`의 0~1000 보정과 이벤트 키 중복 방지를 재사용했다.

## 5. 진행 중 발생한 문제와 해결

### 5.1 #103이 아직 병합되지 않음

이슈 #104는 #103의 퀘스트 진행·인증 구조가 필요하지만 PR #118이 아직 열려 있었다.
`dev`가 아니라 사용자가 승인한 PR #118 HEAD `ccf24d8`을 기준으로 격리 저장소와 새 브랜치를
만들었다. 기존 원격의 동명 #104 브랜치는 건드리지 않았다.

### 5.2 최초 Java 패키지 경로 오인

처음 `com/teenymoney/...` 경로를 찾았지만 실제 패키지는 `com/teenyfin/teenymoney/...`였다.
파일이 없다는 오류를 확인한 뒤 전체 파일 목록에서 실제 경로를 찾았으며, 그 전에는 코드
변경이 없었다.

### 5.3 구조 검색 도구의 Windows 경로 파싱 실패

구조 검색 도구가 이 Windows 경로의 Java 파일을 0개 심볼로 처리했다. 이후에는 빠른 텍스트
검색과 필요한 파일만 UTF-8로 읽는 방식으로 전환했다. 검색 실패를 근거 없이 보완하지 않고
실제 인터페이스, XML, 테스트를 직접 확인했다.

### 5.4 전체 테스트 제한 시간을 너무 짧게 설정

첫 전체 테스트 명령이 기능 오류가 아니라 5초 제한으로 종료됐다. 같은 명령을 충분한 제한
시간으로 다시 실행해 성공을 확인했고, 마지막에는 캐시를 쓰지 않는 `clean build`를 수행했다.

### 5.5 Gradle 캐시 잠금 파일 접근 거부

깨끗한 빌드가 사용자 Gradle 캐시의 `.lck` 파일 접근 거부로 한 번 실패했다. 저장소 파일을
삭제하거나 잠금을 강제로 제거하지 않고, Gradle 캐시 접근 권한을 승인받은 동일 명령으로
재실행했다. 최종 빌드는 23초에 성공했다.

### 5.6 한국어 테스트 로그와 XML 집계 인코딩

PowerShell 콘솔 일부에서 한국어 테스트명이 깨졌고, 기본 인코딩으로 결과 XML을 읽자 일부
파일 파싱 경고가 발생했다. 테스트 결과 자체는 정상이었다. XML을 명시적으로 UTF-8로 읽고
테스트 수를 다시 계산해 `501 / 통과 447 / 건너뜀 54 / 실패 0`을 확인했다.

### 5.7 장문 설계 문서의 예전 명칭

기존 문서에는 UUID 형식 송금 키와 구현되지 않은 예전 오류 코드가 남아 있었다. 이번 확정
설계와 코드에 맞춰 `QUEST_REWARD:{questId}`, `QUEST_FAILED:{questId}` 및 실제 오류 코드로
동기화했다.

### 5.8 문서 패치 문맥 불일치

SQL README의 예상 문맥이 실제 마지막 문장과 달라 첫 문서 패치가 적용되지 않았다. 부분 적용
여부를 확인해 변경이 없음을 검증한 뒤 정확한 문맥으로 다시 적용했다.

### 5.9 외부 DB·Redis 부재

환경변수가 없어 54개 조건부 통합 테스트는 건너뛰었다. 임의의 운영 DB에 연결하거나 자격증명을
추측하지 않았다. 대신 전체 컴파일, WAR 패키징, 447개 테스트, MyBatis XML 등록 및 SQL 형태를
검증했다. 배포 전 실제 MySQL에서 V016·V017 적용과 DB 조건부 테스트 실행이 필요하다.

### 5.10 기존 Gradle 경고

빌드는 성공했지만 저장소가 사용하는 일부 Gradle 기능이 Gradle 9와 호환되지 않는다는 기존
경고가 출력됐다. 이슈 #104 범위와 무관하여 빌드 도구 업그레이드는 포함하지 않았다.

## 6. 배포 전 확인 사항

적용해야 한다.

```text
sql/migration/V016__add_quest_reward_transfer_type.sql
sql/migration/V017__allow_optional_quest_rejection_reason.sql
```

권장 순서:

1. 검증용 MySQL에 V016과 V017 적용
2. `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 설정
3. `.\gradlew.bat clean test` 실행
4. `T_WLT_TRF_L` CHECK에 `QUEST_REWARD`가 포함되고, 사유 없는 `REJECTED` 인증이 허용되는지 확인
5. 현금 보상 승인 한 건으로 부모·자녀 잔액, 양쪽 원장, 송금 상태, 점수 이력, 퀘스트와 인증 상태 확인
6. PR #118 기준이 변경됐다면 이 브랜치를 최신 HEAD에 맞춰 충돌 검토
7. 검토 후 push와 PR 생성
